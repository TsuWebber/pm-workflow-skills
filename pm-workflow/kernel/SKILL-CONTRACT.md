# Kernel — Skill 契約

## 定位

每支 skill 的**「開工前確認」與「落地段」**怎麼寫。**單一維護點——各 `SKILL.md` 只引用這份，
不複製內容。**

共用原則見 [PRINCIPLES.md](./PRINCIPLES.md)。預設語言：繁體中文（技術名詞保留英文）。

---

## 為什麼要固定段名

**跑起來的時候，模型只讀得到當下那一支 `SKILL.md`。** agent 的路由表不在場，
kernel 的原則不在場，上一支 skill 的對話也可能已經被壓縮掉。

所以「這一步接誰的、交給誰、什麼條件下不准往下走」必須寫在每支 skill 自己身上，
而且寫在固定的位置——否則模型不會去找。

**接力棒是檔案，不是對話記憶。** 判斷「上一步做完了沒」一律去看檔案
（不用 status 欄位，見 [PRINCIPLES.md](./PRINCIPLES.md) 第一條），不靠記得。

---

## 固定段名與順序

沿用既有 skill 的骨架（[spec-plan](../skills/spec-plan/SKILL.md)、
[spec-write](../skills/spec-write/SKILL.md)、[from-notion](../skills/from-notion/SKILL.md)
都是這個形狀）：

```
# <Skill Name>（<中文一句話>）

## 定位                          這支 skill 是什麼、在整套裡的位置、不做什麼
## When To Use                   適用 / 不適用（改用別的）
## Step 0：開始<動作>之前先確認  ← 第一個講「怎麼做」的段
## Step 1…N：<流程>
## 落地到 drafts（…都要做）      ← 產物 + 交出去前的放行判斷
## 收尾與銜接                    ← 下一步、這一輪結束的條件
## Writing Rules                 ← 最後一段
```

兩個位置是釘死的：**開工前確認一律是 `Step 0`**（既有 skill 也放在這個位置，例
[from-notion](../skills/from-notion/SKILL.md) 與 [to-notion](../skills/to-notion/SKILL.md)
的 token 成本確認），**落地段與收尾段一律是 `Writing Rules` 前的最後兩段**。

`Step 0` 前面只准放 `## 定位` 與 `## When To Use`，其餘流程節排在它後面。
中間流程節維持自己的編號，**不因段落調整而重編**（跨檔引用按 Step 編號指路）。

---

## 「開工前確認」怎麼寫

四塊，順序固定：

```markdown
## Step 0：開始<動作>之前先確認（不滿足先別<動作>）

這一段與落地段的寫法見 [kernel/SKILL-CONTRACT.md](../../kernel/SKILL-CONTRACT.md)。

**接手的東西 = <一句話：這一步吃什麼>**（<在哪找、預設落點>）。

**放行判斷**（都要有答案才開始）

- [ ] <條件>。<為什麼這一條要擋——寫清楚不擋會發生什麼>
- [ ] <條件>。

**提醒，不擋路**

- <狀況> → <照做，但要講一句>

**不放行時退回**：<退回哪一支 skill，或該去補什麼>
```

**「放行判斷」的每一條都要寫理由**，而且理由要寫「不擋會發生什麼」，不是「這樣比較好」。
沒有理由的擋下條件，下一個人會覺得是形式主義然後繞過它。

範例（寫得好的樣子）：

> - [ ] 答得出「要解的痛是什麼」。掃案例是對著痛掃的——只給一個功能名就開掃，
>       會收回一堆長得像但解的不是同一件事的東西。

**反理性化（這一段不得跳過）**——沿用 [spec-plan](../skills/spec-plan/SKILL.md) 的寫法，
把常見的繞過話術先寫死：「先做再說」「很急」「很小的改動」一律不放行，
理由寫「不擋會發生什麼」。

## 落地段怎麼寫

三塊，順序固定：

```markdown
## 落地到 drafts（每次<動作>都要做）

**產物**：<落哪個路徑、什麼格式>

**交出去前的放行判斷**（全過才交）

- [ ] <檢查項>
- [ ] <檢查項>

**提醒，不擋路**（沒做到會提一句，但可以往下）

- <軟訊號>
```

如果這一步不改某些檔案，**在產物那塊明講**（例：「`spec.md` 一個字都不動」）。
沒明講的話，模型會順手改。

`decisions.md`、`actions.md`、`changelog.md` 一律沿用
[drafts/_meta/](../../drafts/_meta/) 的模板格式，不另立一套寫法。

## 收尾與銜接怎麼寫

```markdown
## 收尾與銜接

- <什麼情況> → <哪一支>
- <什麼情況> → <哪一支>

**這一輪結束的條件**：<一句話：什麼時候算做完了>
```

---

## 分級：哪些擋下、哪些只提醒

**會讓下游建立在假證據上的，設成不放行；其餘只提醒。**

| 擋下 | 只提醒 |
|---|---|
| 無來源的案例 | 案例只掃了 2 個（視野窄） |
| 純意見的痛點（沒有原話、沒有行為、沒有來源） | 實例全來自同一種來源 |
| 憑印象填的欄位（`shot:` 留空、「沒做好的地方」全部空著） | 證據強度全是「轉述」 |
| 窮舉沒掃完就下結論 | 條數明顯偏多（可能太大） |
| 把臆測當事實寫進產物 | 某一節寫得比別節薄 |

一句話怎麼判斷：**這一條放行之後，下游會不會拿它去做決定、而且看不出它是假的？**
會 → 擋。不會 → 提醒。

**擋下的條件不要重複設兩層。** 上一支已經擋過的，下一支不重擋——擋兩次不會擋得更牢，
只會讓兩邊的條件各自長歪，最後互相打架。

## 「章節填了沒」型檢查項的寫法

因為這條線不用 `status` 欄位（見 [PRINCIPLES.md](./PRINCIPLES.md) 第一條），
檢查項一律寫成「哪個檔案的哪一節有沒有內容」：

```markdown
**放行判斷**（都要有答案才開始）

- [ ] `cases/FINDINGS.md` 存在，而且「我們要贏在哪」那一節有結論
      （真的沒有值得補的缺口 → 寫「這一版只求追平」也算有結論，留空不算）。
      沒有它就等於還沒判斷過我們憑什麼比現有方案好，往下寫規格只會寫成功能清單。
```

三個要點：

1. **指到具體的檔案 + 具體的段名**，不要寫「調研做完了」這種判不出來的條件。
2. **「寫『沒有』也算過」要明講**，否則會有人為了過關硬編一條。
3. **理由寫「不擋會發生什麼」**。

## Writing Rules

- 一律繁體中文，語言 PM / 設計 / RD 都看得懂。
- 跨檔引用一律用相對 markdown 連結指到具體檔案（含 `.md`），不用 `[[...]]` wiki 連結。
- 段名照上面的骨架，不自創；中間流程節的編號不因段落調整而重編。
- 每條檢查項都要帶理由，理由寫「不擋會發生什麼」。
- 待釐清的優先級沿用 `actions.md` 的分級：🔴 BLOCK / 🟠 次高 / ⚪ 低風險。
