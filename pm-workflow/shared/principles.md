# Kernel — 共用原則

## 定位

`discovery` 與 `delivery` 兩個 agent 共用的**共用原則**。純原則、零程式碼——它不是 library，
是開工前被讀一次的背景。真正「讓方法論被執行」的力量在各 skill 的步驟與放行判斷。

- **誰讀它**：兩個 agent 開工前讀一次；各 skill 在需要判斷「這件事歸誰、缺了怎麼辦」時回查。
- **誰改它**：要改整條線的共用紀律時。改了兩邊都受影響，所以**不要把單一 skill 的習慣寫進來**
  ——那些歸各自的 `SKILL.md`。

skill 的「開工前確認」與「落地段」怎麼寫，見 [SKILL-CONTRACT.md](./SKILL-CONTRACT.md)。

預設語言：繁體中文（技術名詞保留英文）。

---

## 三層的關係

```
shared/     共用原則（本檔）+ skill 契約。零程式碼，不認識任何 skill
   ▲
   │ 引用（單向）
   │
.claude/agents/     路由：這一段有哪幾支 skill、現在該跑哪支、入口滿足了沒
   │                不抄方法論內容——抄了就會有兩份說法打架
   ▼
skills/           步驟流程 + 放行判斷。方法論真正被執行的地方
```

**依賴方向單向**：skill 依賴 kernel，kernel 對 skill 一無所知。agent 只負責路由與守邊界，
不重複 skill 的內容。

## 兩段的分工

| | discovery | delivery |
|---|---|---|
| 回答 | 這件事值得做嗎、別人怎麼做、痛是真的嗎 | 這件事要做成什麼樣、怎麼驗收 |
| 產物 | `cases/`、`pains/`、`cases/FINDINGS.md` | `spec.md`、`stories.md` |
| 交棒點 | `FINDINGS.md` 的「參考對象」與「我們要贏在哪」都有結論 | `spec.md` §9 AC |

## 五條共用原則

### 一、不用 status 欄位：看檔案、看章節

這條沿用 [CLAUDE.md](../../CLAUDE.md) 已寫死的原則（「規格不用 status 欄位：在不在審看 Gitea
上有沒有開著的 PR；上線與否看資料夾位置」）。

所以放行判斷看的是**這一節填了沒**，不是狀態值翻了沒：

| 想知道 | 看什麼 |
|---|---|
| 案例掃過了沒 | `cases/` 底下有沒有 CASE 檔 |
| 綜合過了沒 | `cases/FINDINGS.md` 在不在 |
| 「沒解好的地方」這個面向掃過了沒 | 每個 CASE 檔的該節有內容，或明確寫「沒查到」 |
| 機會評估做過了沒 | `FINDINGS.md` 有沒有「我們要贏在哪」那一節 |
| 痛點有證據沒 | `pains/` 底下有沒有 PAIN 檔 |

**為什麼這樣就夠**：狀態欄位的價值是「一眼看得出走到哪」，而章節填了沒同樣看得出來，
還少一份會跟內容漂移的元資料。代價是機器檢查要 grep 段名而不是讀欄位——這個 repo 沒有
管線在跑，這個代價不存在。

### 二、缺的要寫出來，不留空

偵測到資料有洞時**明確回報，不臆測填補**。這條對齊 [CLAUDE.md](../../CLAUDE.md) 的
「不臆測：來源沒寫清楚的寫 `TBD（規格未明）`」，並往前延伸到調研段：

- 查不到的寫「沒查到」，不要憑印象填
- 截不到畫面的寫「截不到：<原因>」，不要找一張像的湊上去
- 找不到痛點實例**是要回報 PM 的訊號，不是失敗**——它可能代表這個痛不存在

**留空跟「還沒做」長得一模一樣**，而下游分不出來。所以「沒有」要寫出來，不能省略。

### 三、寫「沒有」也是答案，不是跳過

窮舉類的檢查（三個面向、AC 的十二格檢查表、畫面五態）逐格問過之後，某一格真的沒東西，
就寫「無」+ 一句原因。**這是正確做法，不是敷衍。**

**寫「無」比抄一條既有事實充數好得多**：寫「無」留下的是可覆核的紀錄；抄現有規格的事實
充數會產生一條恆真、永遠 pass、測不出東西的東西，而且它會通過每一道形式檢查。

怎麼分辨：**取材是問它，不是抄它。** 既有規格（[specs/](../../specs/)、[models/](../../models/)）
載明的事實是窮舉的**起點**，用它去想「這件事的哪個行為會使它成立或被破壞」。

### 四、實例不是意見

證據以「原話、行為、可追來源」為準。

- 「使用者覺得結帳很麻煩」——這是**意見**，不能立檔
- 「客服 A，月底對帳時為了核一筆折扣單翻了 40 分鐘紙本，原話『每個月底我都想把這台機器丟掉』」
  ——這是**實例**

三條規則：原話逐字不改寫；事實與詮釋分開；沒有原話就明講是轉述並降證據強度，
不得偽裝成一手。

**來源可追是硬要求**：每個 CASE / PAIN 檔必須記來源（連結、檔案相對連結、或「使用者口述」）。
沒有來源的案例是傳說，下游沒法覆核。

### 五、衍生物不是來源，改要改來源

真相只住在來源檔。衍生物（`stories.md`、prototype、Notion 展示頁、`FINDINGS.md` 的綜合結論）
一律「來源改了重跑」，不手改衍生物。

**在衍生物上改一次，那句話就再也不會回到任何人下次會讀的地方。**

## 圖片與截圖

圖片政策沿用 [CLAUDE.md](../../CLAUDE.md)：**任何圖片不進 repo**。所以 CASE 檔的 `shot:` 欄
只有三種合法值：

| 值 | 什麼時候 |
|---|---|
| Google Drive 連結 | 有截到圖，已上傳 Drive |
| `截不到：<一行原因>` | 要登入、付費牆、App 畫面、或這個來源本來就沒有畫面（純文件研究） |
| `待上傳：<本機暫存位置>` + 一筆 `actions.md` 待辦 | 截到了還沒上傳，**不留在這個狀態超過一輪** |

**不要填本機路徑當永久值**，也不要留空——留空跟「還沒做」分不出來。
要一次把圖搬乾淨用 `pm-intake notion（圖片搬到 Drive）`。

## 交棒點一覽

```
想法 / 問題
  │
  ├─ pm-plan scope ─────────────── 要不要做、碰哪些模組、方向（既有 skill）
  │
  ├─ pm-discover cases ───── 三面向掃案例 → cases/ + FINDINGS.md
  ├─ pm-discover pains ─ 痛點實例 → pains/
  │     （這兩支誰先都行）
  │
  ▼ FINDINGS.md 的「參考對象」與「我們要贏在哪」都有結論
  │
  ├─ pm-spec write ────────────── spec.md 12 節（既有 skill）
  ├─ pm-review qa ───────────── 挑刺（既有 skill）
  ├─ pm-spec story ──────────── stories.md（既有 command）
  └─ prototype ─────────────── 畫面驗證（既有 skill）
```

完整的主流程圖以 [README.md](../../README.md) 的「完整生命週期」為準，這裡只補調研段。

**回收路**：`pm-spec write` 或 `pm-review qa` 撞到「這件事別人怎麼做我們不知道」→ 退回
`pm-discover cases`；撞到「這個痛沒有證據」→ 退回 `pm-discover pains`。

## Writing Rules

[CLAUDE.md](../../CLAUDE.md) 的「撰寫慣例」是基準（繁體中文、跨檔一律用相對 markdown 連結指到
具體檔案、圖片不進 repo、不臆測）。以下是這條線額外的兩條：

- **欄位名只住 frontmatter，正文寫白話。** `lens`、`evidence` 這類欄位名不進正文
  （寫「這是官方文件寫的」而不是「evidence: 官方資料」）。理由：CASE / FINDINGS 的讀者比 spec
  更雜（PM、RD、設計、利害關係人），內部欄位名只有寫的人看得懂。
- **證據強度分四級**：一手體驗 > 官方資料 > 第三方評測 > 轉述。四個詞照抄，不自創。
