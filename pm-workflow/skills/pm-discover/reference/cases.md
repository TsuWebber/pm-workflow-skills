# Discovery Case Scan（掃案例）

## 定位

為一個 feature 收集**解法空間**的案例，收斂成兩個判斷：**照誰做**、**我們贏在哪**。

案例收集不是逛街，是帶著三個明確問題去看：

1. 慣例已經幫我們決定了什麼？
2. 同一個痛，還有哪些解法形狀？
3. 別人在哪裡做不好——我們可以贏在哪？

**這個 skill 不寫 `spec.md`**。它產出的是 `drafts/<sprint>/<feature>/cases/` 底下的調研材料
與兩個收斂判斷，spec 內文歸 `pm-spec write`。

活範例：drafts/2606/product-master/cases/（`<規格庫>/drafts/2606/product-master/cases/`）
（8 個 CASE + FINDINGS）。共用原則見 [`../../../shared/principles.md`](../../../shared/principles.md)。

預設語言：繁體中文（技術名詞保留英文）。

---

## When To Use

適用：

- PM 想知道這件事別人怎麼做、有沒有現成的可以照
- 要判斷某個缺口值不值得補
- `pm-spec write` 或 `pm-review qa` 撞到「這裡的做法沒有依據」被退回來

不適用（改用別的）：

- 要收痛點證據、問「這個痛是真的嗎」 → `pm-discover pains`
- 還在想要不要做、方向沒收斂 → `pm-plan scope`
- 要寫 / 改規格內文 → `pm-spec write`

## Step 0：開始掃之前先確認（不滿足先別掃）

這一段與落地段的寫法見 [`../../../shared/skill-contract.md`](../../../shared/skill-contract.md)。

**接手的東西 = 一個已存在的 feature 資料夾**（`drafts/<sprint>/<feature>/`）
＋**一句話的痛**。痛通常在 `decisions.md` 的問題定義或 `spec.md` §1，找不到就直接問 PM。

**放行判斷**（都要有答案才開始掃）

- [ ] feature 資料夾存在。不存在 → 這一支不建資料夾，退回 `pm-plan scope`
      （它同時負責問清楚方向，代建會跳過那一步）。
- [ ] 答得出「要解的痛是什麼」。掃案例是**對著痛掃**的——只給一個功能名就開掃，
      會收回一堆長得像、但解的不是同一件事的東西，而且事後看不出來哪些不算數。

**提醒，不擋路**

- 這個 session 沒有 web 工具 → 退化為訪談 PM 已知的案例，在 CASE 檔證據強度如實標「轉述」。
- PM 已經有一份競品清單 → 那是掃描起點，落 `cases/README.md` 的待掃清單，別直接當結論。

**不放行時退回**：`pm-plan scope`（把痛與方向問出來、建資料夾）。

## Step 1：三個面向

| 面向 | 問的問題 | 餵哪裡 |
|---|---|---|
| **成品慣例** | 這件事在哪些既有系統做過？慣例長怎樣（入口、流程、預設值、資料模型）？我們照誰抄哪塊？ | FINDINGS 的「參考對象」 |
| **競品解法** | 同一個痛，別人用什麼形狀的解法？各自的取捨是什麼？ | 落子前的發散 + `decisions.md` 的「考慮過的選項」 |
| **沒解好的地方** | 誰做了但做不好、誰根本沒做？**憑什麼說它沒做好？** | FINDINGS 的「大家都沒解好的」→ 機會評估 |

一個案例可以同時餵三個面向（frontmatter 的 `lens` 可多標），但**記錄的東西不同**：
成品慣例記「介面與資料模型長怎樣」、競品解法記「解法的形狀與取捨」、
沒解好的地方記「他們卡在哪、有什麼證據」。

**第三個面向是這一步真正的產值。**「別人怎麼做」只讓我們追平；
**「別人在哪裡做不好」才是我們能贏的地方。**

而且它的取材方式跟前兩個不同——前兩個看官網與文件（廠商想讓你看到的），
第三個要去看 **issue 追蹤、社群抱怨、負評、官方文件裡的自承**（廠商不會主動講的）。

> **廠商不會在官網寫自己哪裡沒做好。** 所以這一節如果只有一句「沒查到」而且沒有任何
> issue 編號、原話、外掛安裝數這類可查證的東西，那一輪很可能只掃了行銷頁面。

**「不借哪塊」與「沒做好的地方」是兩件事，別混**：

| | 講的是 | 例 |
|---|---|---|
| **不借哪塊** | 他們做得好，但**不適合我們的情境** | 「Shopify 是單站台架構，沒有我們同一商品在多地區各自要有獨立銷售單位的需求」 |
| **沒做好的地方** | **他們自己也沒做好**，而且有證據 | 「ChannelAdvisor 的組合關係一旦上架就鎖死，事後改不了」 |

前者是取捨，後者是機會。**只有後者會往下走到 Step 6 的機會評估。**

## Step 2：素材來源（依 session 能力退化，不硬求）

1. **網路研究**（有 web 工具時）：官方文件、API reference、changelog、第三方評測、
   issue 追蹤、社群討論。**先問 PM「你已知的參考系統有哪些」再往外擴**，不要憑空猜名單。
2. **PM 提供的素材**：內部競品分析、截圖、先前的調研文件——照檔整理進 CASE 格式。
3. **競品實測**（有瀏覽器、要看實際行為或後台設定時）：先跑 [`compete`](compete.md)，它產出的 CASE 檔格式相同，直接拿來做 Step 4～6，不用重掃。
4. **訪談 PM 腦中的知識**（無外部工具時的底線）：一次一問，把用過 / 看過的案例問出來。
   受限於 PM 視野，證據強度如實標「轉述」。

**來源可追是硬要求**：每個 CASE 檔必須記來源（連結 / 檔案相對連結 / 「使用者口述」）。
沒有來源的案例是傳說，下游沒法覆核。

### 截圖與 `shot:` 欄

圖片政策見 [`../../../shared/principles.md`](../../../shared/principles.md)：**圖片不進 repo**。
所以 `shot:` 只有三種合法值——Drive 連結、`截不到：<原因>`、
或 `待上傳：<本機位置>` 加一筆 `actions.md` 待辦（要一次搬乾淨用 `pm-intake notion（圖片搬到 Drive）`）。

**不要填本機路徑當永久值，也不要留空**——留空跟「還沒做」分不出來。

純資料模型 / API 的文件研究本來就沒有畫面可截，直接寫
`截不到：文件研究，無對應畫面`，這是正確答案不是偷懶。

## Step 3：CASE 檔模板

一案例一檔，放 `cases/CASE-NNN-<slug>.md`（NNN 三位數，slug 英文短語）。
**段名與順序不得自創**——既有的八個檔已經是這個格式，照抄：

```markdown
---
lens: []                  # 成品慣例 | 競品解法 | 沒解好的地方（可多標）
opportunity:              # 這個案例回答的是哪個痛
source:                   # 連結 / 檔案相對連結 / 使用者口述 —— 沒來源不得立檔
evidence:                 # 一手體驗 | 官方資料 | 第三方評測 | 轉述
collected:                # YYYY-MM-DD
shot:                     # Drive 連結 | 截不到：<原因> | 待上傳：<位置>
---

# CASE-NNN — <對象：哪個系統的哪個功能>

## 觀察

<它怎麼做：入口、流程、資料模型、關鍵設計決定。寫事實，不寫評論。>

## 可借哪塊

<照抄哪些慣例 / 機制 + 為什麼適用我們的情境>

## 不借哪塊

<哪些不適用 + 一行理由（情境差異在哪）>

## 沒做好的地方

<他們做了但做不好、或根本沒做的地方。**每一條都要有證據**：
 - issue / 討論串編號與開了多久
 - 使用者原話（負評、社群抱怨）
 - 官方文件裡的自承（「本功能不涵蓋…」）
 - 生態的代償（為了補這個缺口長出幾個外掛、最大的裝多少）
 沒查到就寫「沒查到」，不要憑印象填>
```

`cases/README.md`（選填）三塊：**待掃清單**（PM 給的參考名單，掃完移進索引）、
**索引**（一行一案例：編號、對象、面向、一句結論）、**掃過但不值得立檔**（免得下次重掃）。

日期用使用者提供的當天日期，不自行捏造。

## Step 4：FINDINGS 綜合

一次掃出好幾個案例時，直接跳去收斂會漏掉**跨案才看得到的東西**：
哪個做法是多數慣例、哪個只是單家特色、哪裡大家分歧。

所以在 CASE 檔與收斂之間補一層綜合地景，落 `cases/FINDINGS.md`。**這一份必產。**

**掃完、收斂前先問一句熟悉度**——它決定寫完整版還是簡版，**不決定寫不寫**：

> 掃到 N 個案例。你對「<這類功能>」熟不熟？
> 不太熟 → 我寫完整版：每個主題記慣例層級、收斂、分歧、啟示。
> 很熟、心裡有數 → 我寫簡版：只列主題名、哪幾個案例、一句啟示。

模板（**段名沿用既有那份，不另立**）：

```markdown
# <feature> — Findings 綜合地景

**涵蓋案例**：CASE-001 … CASE-00N（共 N 個：<對象清單>）
**綜合日**：YYYY-MM-DD
**使用者熟悉度**：<高 | 中 | 低>（決定完整版還是簡版）

## 主題地景

### <主題名>

- **慣例層級**：跨業慣例 | 同類慣例 | 單家特色
- **收斂**：哪些案例這樣做（CASE-NNN, CASE-NNN）—— X/N
- **分歧**：誰不一樣、為什麼（CASE-NNN）    ← 簡版可省
- **啟示**：對我們的一句話傾向

## 大家都沒解好的

### <缺口>

<誰沒解好、什麼事、證據是什麼>

## 待釐清（選填）

<兩個都對但互斥的方向，交給 PM 拍板；同時轉一筆進 actions.md>

## 參考對象

<Step 5 的三擇一判斷 + 照誰做、借哪一塊、哪裡刻意不一樣>

## 我們要贏在哪

<Step 6 機會評估判「做」的那幾筆；沒有值得補的缺口就寫「這一版只求追平」>
```

**「收斂」那一行一定要指得到 CASE 編號。** 沒有編號的主題等於沒有依據，
而且下游要回頭查是哪幾個案例支撐它時查不到。

## Step 5：收斂——參考對象

案例掃完必須收斂，不能留一堆檔案讓下游自己看。對整個 feature（或逐流程步驟）
下判斷，三者擇一，寫進 `FINDINGS.md` 的「參考對象」節：

| 判斷 | 什麼情況 | 下游怎麼走 |
|---|---|---|
| **整套照著做** | 慣例成熟，照 <對象> 的做法就對了（CASE-NNN） | `pm-spec write` 直達 |
| **拆開各借一塊** | 沒有同類成品，但問題拆得開，各部分在別的系統各自被解過 | 借來的每一塊各照其慣例做；**縫合處若無前例、且組合方式影響方向 → 那一塊轉一筆進 `actions.md` 標 🔴 BLOCK** |
| **沒有現成的可以照** | 掃過了、真的沒有 | **這是要回報 PM 的訊號，不是照填**（見下） |

**「沒有現成的可以照」怎麼處理**：把「這個做法可行」寫成 `actions.md` 一筆待釐清、
標 🔴 BLOCK、影響 spec 節寫明哪一節，讓 PM 在開工前決定要不要先做小範圍試探。

**不要默默放行給 `pm-spec write`。** 那會變成在寫規格的時候發明一套沒人驗過的做法，
而它讀起來跟有依據的規格長得一模一樣。

同時在 `decisions.md` 落一則 D-x（用它自己的模板格式），把「考慮過的選項」
填上競品解法面向發散過的那幾種——**發散過的選項要留，防日後重新提案。**

## Step 6：機會評估——補這個缺口划不划算

Step 5 收斂「我們照誰做」；這一節收斂「**我們哪裡可以做得更好**」。
兩者都要，而且後者是這一步真正的產值——照著慣例做只會追平。

**輸入**：FINDINGS 的「大家都沒解好的」。**逐缺口填一張表**，
填不出來的欄就寫「不知道」，不要用形容詞蓋過去：

| 欄 | 問什麼 | 不可以寫什麼 |
|---|---|---|
| **缺口** | 一句話：誰沒解好、什麼事 | 不寫解法 |
| **現在使用者怎麼撐** | 沒有這個功能時，他們**實際**在做什麼（手動、外掛、Excel、放棄） | 不寫「很不方便」——要寫他做的動作 |
| **不補會怎樣** | 具體後果與頻率；有數字寫數字 | 不寫「體驗不好」 |
| **補起來大概多大** | **量級不是估時**：小（既有東西加一段）/ 中（要新做一塊）/ 大（要動資料模型或跨模組）＋ 一句依據 | 不寫人天，那是工程的事 |
| **補起來換到什麼** | 對得上 `spec.md` §1 哪個成功條件；誰會有感、怎麼看得出來 | 不寫「提升競爭力」 |
| **判斷** | 做 / 先確認 / 不做 ＋ 一行理由 | 不留空 |

**三種判斷的去處**：

| 判斷 | 什麼情況 | 落到哪 |
|---|---|---|
| **做** | 量級撐得住換到的結果，做法沒有方向上的不確定性 | FINDINGS 的「我們要贏在哪」→ 下游進 `spec.md` |
| **先確認** | 值得做，但做法有方向不確定性 | `actions.md` 一筆，標 🔴 BLOCK |
| **不做** | 量級撐不住、或不在這個 feature 的邊界內 | `spec.md` §2 Scope (Out)，**附上這裡的理由** |

> **「不做」也要寫進去，而且要帶理由。** 一句「這一版不做」跟
> 「不做未使用素材清單——引用的不存在無法證明，每一個把假設當事實呈現的清理功能都造成過事故」
> 是完全不同的東西：前者三個月後會被人當成漏掉而重新提出，後者可以直接擋掉那次討論。

### 量級怎麼估才不算亂猜

**先扣掉我們已經有的。** 估之前先確認這個缺口要補的行為，是不是有一段
**specs/（`<規格庫>/specs/`） 裡早就有別的模組在做**。沒扣掉會把已經有的東西算成要付的成本，
量級整個估大——而量級估大的直接後果是這個缺口被判「不做」。

這一步不估時，但**可以從調研本身推量級**，依據比拍腦袋硬：

- **生態的代償規模**：為了補這個缺口，別人的生態長出幾個外掛？最大的那個裝多少？
  有十一個外掛在補同一個洞，代表它不是小工程，而且原廠不想碰。
- **開了多久沒解**：核心 issue 掛了九年半，通常不是沒人想做，是動到根。
- **做到的那幾家付出什麼**：有的那幾家是不是同時放棄了別的東西？

**三個訊號都指向大時，別在這一版排它**；都指向小卻沒人做，反而要先問一句
「**是不是有我們還不知道的理由**」——那通常是該轉一筆 `actions.md` 待釐清的訊號。

## 落地到 drafts（每次掃完都要做）

**產物**：

- `drafts/<sprint>/<feature>/cases/CASE-NNN-<slug>.md`——一案例一檔（模板見 Step 3）
- `drafts/<sprint>/<feature>/cases/FINDINGS.md`——綜合地景 ＋ 參考對象 ＋ 我們要贏在哪
- `decisions.md` 一則 D-x（參考對象的判斷 + 考慮過的選項），用它自己的模板格式
- `actions.md` 若干筆（判「先確認」的、以及「沒有現成的可以照」升上來的）

**`spec.md` 一個字都不動。** 這一步的結論落 `FINDINGS.md` 與 `decisions.md`，
spec 內文歸 `pm-spec write`——直接寫進 spec 會跳過 PM 拍板那一步。

**交出去前的放行判斷**（全過才交）

- [ ] 每個 CASE 檔符合 Step 3 模板，且**來源可追**（無來源不得立檔）。
- [ ] **「沒做好的地方」這個面向掃過**——每個 CASE 檔的該節有內容或明確寫「沒查到」。
      **全部 CASE 都空著 → 擋下**，那代表只看了官方文件，沒看 issue 與負評。
- [ ] 每個 CASE 檔的 `shot:` 是三種合法值之一（Drive 連結 / 截不到：原因 / 待上傳）。
      **留空 → 擋下**，因為留空跟「還沒做」分不出來。
- [ ] `cases/FINDINGS.md` 存在（完整版或簡版都算），每個主題的「收斂」那行指得到 CASE 編號。
      沒有 → 擋下：下游要回頭查依據時查不到。
- [ ] **「參考對象」已收斂**，三擇一，正文寫照誰做與借哪塊。
      答「沒有現成的可以照」→ 已轉 `actions.md` 標 🔴 BLOCK，**沒有默默放行**。
- [ ] **「我們要贏在哪」已填**——每一筆帶「補起來大概多大」與「換到什麼」；
      真的沒有值得補的缺口 → 寫「這一版只求追平」，**不得留空**。
      判「不做」的缺口已帶理由，準備寫進 `spec.md` §2 Out。
- [ ] 正文沒有欄位名（`lens`、`evidence` 只住 frontmatter，見
      [`../../../shared/principles.md`](../../../shared/principles.md)）。

**提醒，不擋路**（沒做到會提一句，但可以往下）

- 掃完、收斂前**問一句熟悉度**（Step 4）：它決定 FINDINGS 寫完整版還是簡版。
- 競品解法面向至少掃過 2–3 個對象再落子（單一案例就收斂 → 視野太窄）。
- 證據強度全是「轉述」→ 提示找至少一個一手或官方來源。
- 「沒做好的地方」全部只有一句話、沒有 issue 編號 / 原話 / 安裝數 → 提示這一輪
  可能只掃了行銷頁面。

> 資料夾 / 檔案的建立**不需要 PM 碰 git**；之後要送出用 `pm-ship`。

## 收尾與銜接

- 痛點還沒有實例證據 → `pm-discover pains`（誰先都行）。
- 兩邊都齊了 → `pm-spec write` 寫 `spec.md`。
- **收斂不了**（掃了一輪還是說不出照誰做）→ 那多半是痛本身太模糊，
  回頭把痛講清楚再掃一輪；不要靠多掃十個競品硬湊。

**這一輪結束的條件**：三個面向都掃過，「參考對象」與「我們要贏在哪」都有結論、不留空。

## Writing Rules

- 一律繁體中文，語言 PM / 設計 / RD 都看得懂（技術名詞如 API path、欄位名保留英文）。
- 寫事實與來源，不寫形容詞。「很不方便」「體驗不好」這類句子在這裡沒有資訊量。
- 查不到的寫「沒查到」，截不到的寫「截不到：<原因>」，**不臆測填補**。
- 欄位名只住 frontmatter，正文寫白話。
- 跨檔引用一律用相對 markdown 連結指到具體檔案（含 `.md`）。從
  `drafts/<sprint>/<feature>/cases/` 引用現況規格要退四層，例
  `[coupon](../../../specs/docs/05-product-and-marketing/coupon/_index.md)`；
  對話中回報時用 workspace 根相對路徑即可。不要用 `[[...]]` wiki 連結。
- **圖片不進 repo**：一律上 Google Drive 只留連結。
- 未定案的不臆測 → 進 `actions.md`；「為什麼」進 `decisions.md`。
