# Discovery Pain Evidence（收痛點證據）

## 定位

把「我們覺得使用者會痛」變成「這裡有 N 個可追溯的實例」。

規格 §1 寫的現況痛點通常是一句話。這一步的工作是幫它**找到實例**——
真實的人、真實的情境、真實的原話。找不到，也是重要結果（見 Step 5）。

**這個 skill 不寫 `spec.md`**。它產出的是 `drafts/<sprint>/<feature>/pains/` 底下的實例
與一則有依據的痛點結論，spec 內文的實際修改歸 `pm-spec write`。

慣例對齊同層的 cases/（`<規格庫>/drafts/2606/product-master/cases/`）（一實例一檔 +
frontmatter 記來源）。共用原則見 [`../../../shared/principles.md`](../../../shared/principles.md)。

預設語言：繁體中文（技術名詞保留英文）。

---

## When To Use

適用：

- PM 手上有一批回饋 / 客服紀錄 / 支援票要消化成證據
- 要確認 `spec.md` §1 或 `decisions.md` 寫的痛點站不站得住
- `pm-review qa` 挑出「這條規則解的痛沒有依據」被退回來

不適用（改用別的）：

- 要看別人怎麼做、找參考案例 → `pm-discover cases`
- 還在想要不要做、方向沒收斂 → `pm-plan scope`
- 要把一場會議整理成決策 / 待辦 → `pm-intake meeting`

## Step 0：開始收之前先確認（不滿足先別收）

這一段與落地段的寫法見 [`../../../shared/skill-contract.md`](../../../shared/skill-contract.md)。

**接手的東西 = 一句話的痛**（在 `decisions.md` 的問題定義或 `spec.md` §1，找不到就直接問 PM）
＋**素材**。

**素材**：問 PM 手上有什麼——用戶回饋、客服對話、支援票、營運 / 客服口述、
內部抱怨、社群留言、訪談記錄。有素材 → 走整理；沒素材 → 走訪談（Step 3）。

**放行判斷**（都要有答案才開始收）

- [ ] feature 資料夾存在。不存在 → 退回 `pm-plan scope`，這一支不建資料夾。
- [ ] 有一句話講得出「要驗的痛是什麼」。收證據是**對著一個痛**收的——
      沒有那句話，收回來的東西無從判斷算不算數，最後會變成一疊「使用者說想要 X」。

**提醒，不擋路**

- 這個痛只有 PM 的自述、還沒有任何素材 → 可以起步，先把那句話寫下來標
  「未驗證 · PM 自述」，**這一步的工作就是替它找實例**。
- 素材是會議記錄 → 先跑 `pm-intake meeting` 消化，再回來抽實例（避免兩邊各記一份）。

**不放行時退回**：`pm-plan scope`（把痛問出來、建資料夾）。

---

## Step 1：核心紀律——實例不是意見

一條可用的痛點證據長這樣：**具體的誰 + 具體的情境 + 掙扎時刻 + 原話 / 行為**。

- 「使用者覺得結帳很麻煩」——這是**意見**，不能立檔。
- 「客服 A，月底對帳時為了核一筆折扣單翻了 40 分鐘紙本，原話『每個月底我都想把這台機器丟掉』」
  ——這是**實例**。

三條規則：

1. **原話必留、逐字、不改寫。** 原話是證據的 DNA，改寫過就只剩你的詮釋。
2. **事實與詮釋分開。** 觀察到什麼（他做了什麼、說了什麼）歸事實；
   你認為它代表什麼，歸 Step 5 匯總時的詮釋，**不寫回 PAIN 檔**。
3. **沒有原話就明講。** 標「轉述」並降證據強度，不得偽裝成一手。

---

## Step 2：一個實例還是多個實例

怎麼分：看**「具體的人在具體情境卡住」出現幾次**，不是素材有幾份：

| 情況 | 怎麼落 |
|---|---|
| 一份訪談裡出現三個不同的卡點 | 抽成三個 PAIN 檔 |
| 十張支援票講同一件事 | **一個** PAIN 檔配十個來源——那是頻率證據，寫進「頻率 / 嚴重度」欄 |
| 同一件事、不同角色卡的點不同（客服 vs 營運） | 兩個 PAIN 檔，「誰」欄不同 |

---

## Step 3：收集方式

- **整理既有素材**：逐份讀，凡出現「具體的人在具體情境卡住」就抽成一個 PAIN 檔。
- **訪談**（沒素材時的底線）：一次一問，問**過去真實發生的事**，不問假設性未來。

  > 問：「上次遇到這問題是什麼時候？當時你（或那位同事）在做什麼、卡在哪？」
  > 不問：「你會不會想要 X 功能？」

  產出的實例來源標「使用者口述」，證據強度標「轉述」（除非 PM 本人就是當事人）。

**這一步不代替訪談。** 真的要去問客服 / 營運 / 用戶的，這支 skill 產出的是**問題清單**，
執行由人；問完回來再落檔。不假裝能替你跑訪談。

---

## Step 4：PAIN 檔模板

一實例一檔，放 `pains/PAIN-NNN-<slug>.md`。**段名與順序不得自創**：

```markdown
---
source:                   # 回饋出處 / 支援票編號 / 會議檔相對連結 / 使用者口述
occurred:                 # 日期或期間
evidence:                 # 一手（原話 / 行為） | 轉述
collected:                # YYYY-MM-DD
---

# PAIN-NNN — <一句話：誰在什麼情境卡住>

**誰**：<具體角色 / 人物代號，不是「使用者」>
**頻率 / 嚴重度**：<多常發生 / 卡多久 / 造成什麼損失。有數字寫數字>

## 情境

<當時在完成什麼任務、走到哪一步>

## 卡在什麼

<掙扎時刻：期望發生什麼 vs 實際發生什麼>

## 原話引述

> <逐字引述，不改寫。無原話 → 記「無原話，轉述自 <來源>」>

## 現在怎麼撐

<現在怎麼繞過？具體步驟（手動、Excel、外掛、找人問、放棄）。
 沒有 workaround 也要記——可能痛不夠深，也可能被徹底卡死，判讀留給 Step 5>
```

`source` 欄引用 repo 內的檔案時用相對 markdown 連結
（例 `[2026-06-16-架構討論.md](../meetings/2026-06-16-架構討論.md)`），
這條沿用 CLAUDE.md（`<規格庫>/CLAUDE.md`） 的「提到檔案就要能點得開」。
日期用使用者提供的當天日期，不自行捏造。

## Step 5：匯總與回檢

實例收完，把結論寫出去。**詮釋寫在這裡，不寫回 PAIN 檔。**

### 1. 落 `decisions.md` 一則 D-x

用它自己的模板格式（`<規格庫>/drafts/_meta/TEMPLATE-decisions.md`）。「背景 / 問題」那欄
寫一句有依據的痛點結論 + 支撐的 PAIN 編號清單 + 整體證據強度：

> **背景 / 問題**：客服每月結帳期為了核對折扣單平均花 40 分鐘以上翻紙本，
> 一個月至少發生 6 次（PAIN-001、PAIN-003、PAIN-004；證據強度：一手，含原話 2 筆）。

### 2. 校準 `spec.md` §1 的現況痛點

證據會讓那句話更具體（誰、什麼情境浮出來了）——**校準措辭，但不改痛的本體**。
要改本體（發現真正的痛是別的）→ 那是方向變了，回 `pm-plan scope` 或落一則新的 D-x。

> `spec.md` 的實際修改**交給 `pm-spec write`**（它負責落 `changelog.md` 與 `spec_version`）。
> 這一步只提出要改成什麼，不自己動 spec。

### 3. 回檢：證據支撐那句痛嗎

- **支撐** → 結論就位，往下走。
- **不支撐 / 找不到實例** → **這是要回報 PM 的訊號，不是失敗。**
  轉一筆進 actions.md（`<規格庫>/drafts/_meta/TEMPLATE-actions.md`），標 🔴 BLOCK：
  「這條痛點目前沒有實例支撐，開工前要確認它是否存在」。

  **不要為了讓規格好看而降低立檔標準。** 找不到實例有兩種可能——
  這個痛不存在，或我們找錯地方。兩種都必須讓 PM 知道，因為第一種代表整個 feature
  的前提有問題，而它在規格上看起來跟第二種一模一樣。

## 落地到 drafts（每次收完都要做）

**產物**：

- `drafts/<sprint>/<feature>/pains/PAIN-NNN-<slug>.md`——一實例一檔（模板見 Step 4）
- `decisions.md` 一則 D-x（痛點結論 + PAIN 編號 + 證據強度）
- `actions.md` 若干筆（證據不支撐時的 🔴 BLOCK、以及要去問誰的訪談清單）

**`spec.md` 一個字都不動。** §1 的校準只提出建議，實際修改交 `pm-spec write`
（它負責落 `changelog.md` 與 `spec_version`）。

**交出去前的放行判斷**（全過才交）

- [ ] 每個 PAIN 檔符合 Step 4 模板；**有原話或一手行為證據，或如實標「轉述」**。
      無來源、純意見（「我覺得使用者會痛」）**不得立檔**。
- [ ] 原話逐字未改寫。改寫過的原話等於沒有原話——它只剩詮釋。
- [ ] `decisions.md` 的痛點結論已寫：一句結論 + PAIN 編號 + 整體證據強度，**不內嵌長文**。
- [ ] 證據不支撐那句痛時**已轉一筆 `actions.md` 標 🔴 BLOCK**，未灌水放行。
- [ ] 正文沒有欄位名（`evidence` 只住 frontmatter，見
      [`../../../shared/principles.md`](../../../shared/principles.md)）。

**提醒，不擋路**（沒做到會提一句，但可以往下）

- 實例全部來自同一種來源（如全是支援票）→ 提示證據單一，補一種來源。
- 實例少於 3 個就下結論 → 提示樣本太薄，或明確標「初步證據」。
- 「現在怎麼撐」全部空著 → 提示這一欄常是量級的最好線索
  （有人為此每月花 40 分鐘，跟沒人在意，是兩件事）。
- 訪談中冒出的新痛（不屬於這個 feature）→ 記下回報 PM，**不擅自擴 scope**。

> 資料夾 / 檔案的建立**不需要 PM 碰 git**；之後要送出用 `pm-ship`。

## 收尾與銜接

- 解法空間還沒掃過 → `pm-discover cases`（誰先都行）。
- 兩邊都齊了 → `pm-spec write` 寫 `spec.md`。
- **證據找不到**是要回報 PM 的訊號、不是失敗：如實回報「這條痛的存在性可能不成立」。

**這一輪結束的條件**：那句痛有實例撐得住（或已如實回報撐不住），
`decisions.md` 的結論寫完、每筆都指得到 PAIN 檔。

## Writing Rules

- 一律繁體中文，語言 PM / 設計 / RD 都看得懂（技術名詞保留英文）。
- 原話逐字引述，不改寫、不潤飾、不合併兩個人的話。
- 事實與詮釋分開：PAIN 檔只寫觀察，詮釋寫在 `decisions.md`。
- 沒有原話就明講是轉述並降證據強度，**不得偽裝成一手**。
- **不要為了讓規格好看而降低立檔標準。** 證據不足如實標低信心，不灌水。
- 跨檔引用一律用相對 markdown 連結指到具體檔案（含 `.md`）。從
  `drafts/<sprint>/<feature>/pains/` 引用現況規格要退四層；對話中回報時用 workspace
  根相對路徑即可。不要用 `[[...]]` wiki 連結。
- **圖片不進 repo**：客服截圖、單據影本一律上 Google Drive 只留連結；
  含真實客戶 / 統編的影本上傳前先確認可分享範圍。
