# retro：專案回顧

## Overview

把一個專案（例如月結訂單銷貨／銷退）從開始到上線的對話與紀錄，整理成團隊可以開會討論的 Retro 文件。

預設輸出語言：繁體中文。
預設輸出位置：本地 Markdown 檔（與資料來源同資料夾）。**不自動寫進 Notion**；使用者要寫進去時再處理（見「寫進 Notion」）。

這份文件的核心不是流水帳，而是**使用者親自挑過的結論**。流程分兩段：先出完整草稿，再用選擇題逐條收斂。

---

## 輸入

使用者可能給下列一種或多種：
- DingTalk 群組匯出 JSON（專案群組）
- DingTalk 一對一匯出 JSON（關鍵利害關係人，常夾雜其他專案）
- Notion 專案紀錄頁（PM 自己維護的逐日紀錄，通常最完整）
- Jira／SPEC 連結

不確定的來源先問清楚「這份跟專案有沒有關」，不要整份塞進文件。

---

## 流程

### 1. 解析資料

環境可能沒有 python／node，**用 PowerShell 的 `ConvertFrom-Json`**：
- 讀 JSON，把 `created_at`（毫秒時間戳）轉成本地時間。
- 只留 `content_text` 有內容的訊息（圖片可標 `[圖片]`），輸出成 `日期時間 | 發送者 | 內容` 的純文字檔，放 scratchpad。
- 一對一檔案先用關鍵字篩出與專案相關的內容，再逐份閱讀；整份是別的專案就不要合併，直接告訴使用者並問要不要另外處理。

資料更新時（使用者說「重撈」「有更新了」）：先比對檔案大小與修改時間；沒變就如實說沒變，不要假裝重做。

### 2. 先查覆蓋範圍，再下結論

- 每份資料先確認**最早與最晚一則的日期**，以及有沒有空窗期。
- 看到「某段期間沒有訊息」時，**不要直接推測原因**。先問使用者或對照 Notion 紀錄；這個專案實際上那段期間每天都有 Sync，只是沒在群組留下記錄，早期的推測就是錯的。
- 資料來源之間衝突時（群組說 A，Notion 標「推翻」），以使用者維護的 Notion 紀錄為準，並在文件中註明。

### 3. 出完整草稿

文件結構（摘要在前，附錄收合）：

1. 標題與資料來源（標明各來源的標籤，如 `[群組]`、`[DM:對象]`、`[Notion]`）
2. **Retro 要點摘要**
   - 專案數字回顧
   - Keep：做得好的地方
   - Problem：做不好的地方
   - Try：下次可以試的做法
3. **附錄**（每個用 `<details><summary>` 收合）
   - 時間軸總覽
   - 關鍵事件、變化與推翻的決策
   - 逐日重點記錄
   - 一對一對話補充（依對象）

寫作規則：
- 每一點附證據（日期＋來源標籤）。沒有證據的使用者自評，標明「來源：PM 自評」，不要編造具體案例。
- 區分「事實」與「我的推論」。推論要明說，例如括號補充的詮釋，被使用者指出解讀反了就要更正。
- Keep／Problem 先寫寬一點（各 8~10 條），讓使用者刪；不要一開始就只列幾條。
- **Try 不要用表格**，用條列：`**Try N｜標題**（對應 Px，優先級）` 加子項（做法、Owner、期限、待定項）。

### 4. 用選擇題逐條討論

草稿出完，使用者說要討論時：
- 用 AskUserQuestion，**每批 3~4 題**，一題對應一條 Try 或 Problem。
- 選項 2~4 個，第一個放建議並標 `(Recommended)`；一定要有「維持現狀」或「不新增」這類出口。
- 使用者常會寫自己的答案（例如「希望有全自動流程」「不認同」「交給 QA 自行決定」），**照他寫的為準**，不要硬套選項。
- 一批答完立刻回寫文件，再開下一批。
- Try 討論完，再回頭用同樣方式確認 Keep 與 Problem 的認定是否正確。

### 5. 回寫與整理

- 被使用者否決的項目：**直接整段刪除**，不要留刪除線或「已討論」標籤。
- 刪除後**順序遞補**：K／P／Try 編號重排，並同步修正文中所有交叉引用（表格欄「對應 Problem」、`見 Try #N`）。
- 「待確認／後續追蹤」這類收尾章節，使用者說刪就整段刪，並提醒只出現在那裡的項目會一起消失。
- 改文件前備份一份到 scratchpad。

## 寫進 Notion

- 公開發布頁（`*.notion.site`）不在 workspace 的 API 權限內，**讀得到不代表寫得進去**。讀它可以用瀏覽器開頁面取文字（頁面是 JS 渲染，要等載入完成）。
- 要寫入，頁面必須在使用者的 workspace 底下並分享給 Claude 的 integration；否則給使用者兩個選擇：自己貼（我先轉成 Notion 格式），或在 workspace 另建新頁。
- Notion 不一定吃 `<details>`；貼之前先問要不要轉成 toggle 與 Notion table 格式。
- 沒寫進去就直說「沒有」，不要含糊帶過。

## 不適用

- 只是要寫 release note → `pm-launch release`
- 只是要寫週報 → `pm-report weekly`
- 要寫 PRD／AC → `pm`
- 單純要通用的 sprint retro 引導（沒有對話資料）→ 用 `pm-execution:retro`
