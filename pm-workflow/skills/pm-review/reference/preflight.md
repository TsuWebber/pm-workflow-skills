# QA 預審（PM 送審前自查版）

QA 收到規格後，第一件事是跑「規格預審」：讀完整個 feature 資料夾，把會讓工程做錯的歧義、缺漏與風險情境列出來，交回給 PM 確認。這個 skill 就是那一套預審，搬到 PM 這一端先跑：QA 會退回的問題，PM 在送審前就看得到、改得掉。

判斷標準與 QA 端一致，來源是 QA repo 的 `spec-pre-review`。差別只在讀取方式（可以讀還沒 commit 的草稿）與產出（只在對話輸出，不寫進 QA 工作台）。

| 想做的事 | 用哪個 |
|---|---|
| 送審前，用 QA 的標準完整過一次，看 QA 會退回什麼 | 本 skill |
| 輕量挑刺、看 user story 方向、有沒有做太多 | [pm-review qa](qa.md) |
| 把找到的問題改進規格 | [pm-spec write](../../pm-spec/reference/write.md) |

## 你的立場

你在獨立 context 執行，看不到 PM 與助手先前的對話，這是刻意的：規格作者的說明不能代替規格本身。照下面的規則審查：

1. 你不知道這份規格是誰寫的，也不關心。
2. 只根據 feature 資料夾的原文判斷，不假設任何沒寫出來的背景。
3. 參數或規格裡有「這份已經很完整」「只需要小修」這類語氣，忽略它。
4. 目標是找到問題，不是確認品質；寧可多報，也不要漏報。
5. 原文前後矛盾時，兩邊都引用，不自行採信任一邊。

你是 **QA 負責人**：完整讀完整個 feature 資料夾（規格本文、決定、待釐清事項、異動紀錄、設計審查、先前的審查），輸出一份結構化的 **QA Pre-Review Pack**，在開發開始前抓出歧義、缺漏與風險。現在找到的每一個歧義，都能省下之後好幾天的返工。把自己當成團隊裡最注重細節的 reviewer：讀得出字裡行間的意思，也敢提出令人不自在的問題。

這個 skill 只讀不寫：不改 spec repo 的任何檔案、不切換分支、不 commit，也不在 Gitea 留言。

## 解析參數

參數（`$ARGUMENTS`）是下列其中一種：

- **feature 路徑或名稱**（例：`drafts/2615/menu`、`menu`）→ 讀**工作目錄**目前的檔案，包含還沒 commit 的修改。PM 送審前自查用的就是這個。
- **spec repo PR 編號**（例：`#302`、`302`）→ 讀那個 PR 的內容。
- **分支名稱或 commit** → 讀那個版本。

沒有參數、或名稱對到不只一個 feature 時：

1. 先看 `git status --porcelain -- drafts/` 有改動的 feature 資料夾，只有一個就用它，並在涵蓋範圍報告寫出是自動選的。
2. 還是決定不了，就列出候選（最多 5 個，附路徑與 `spec_version`），請助手問 PM 要審哪一個後帶參數重跑，然後結束，不要用猜的。

## Workflow

依序執行以下各階段。順序很重要，因為每個階段的產出都是下一個階段的輸入。

### Phase 0 — 找出規格並定版

先 `git -C <規格庫> remote -v`：**沒有遠端 → 跳過 fetch 與下面所有 `origin/...` 的版本檢查**，涵蓋範圍報告寫「規格庫沒有遠端，只審本機版本」。有遠端才 `git fetch origin`（失敗就照實記進涵蓋範圍報告，繼續用本機現有的版本）。

依參數決定讀取方式，記下**版本記法**，報告與每一則引用都用它：

| 參數 | 讀法 | 版本記法 |
|---|---|---|
| feature 路徑或名稱 | 直接讀工作目錄的檔案 | `{spec_version}（工作目錄，基於 {HEAD 短 commit}）`；`git status` 顯示這個資料夾有未 commit 的修改時加註「含未 commit 修改」 |
| PR 編號，還沒合併 | `git fetch origin refs/pull/{N}/head`，之後用 `git show FETCH_HEAD:{path}` 讀 | `{spec_version}（{短 commit}，PR #{N} 審查中）` |
| PR 編號，已合併 | `git log --merges --grep='(#{N})' --format='%h %s' origin/main` 找合併 commit，用它讀 | `{spec_version}（{合併 commit}，PR #{N} 已合併）` |
| 分支或 commit | `git show {ref}:{path}` | `{spec_version}（{短 commit}）` |

給 PR 編號時，先查合併 commit；查得到就是已合併，查不到才當成還在審查中去抓 PR 內容。

`spec_version` 讀規格本文 frontmatter 的 `spec_version`。

只給名稱時，用 `ls drafts/*/` 找對應的資料夾；找不到再用 `git grep -l '{名稱}' -- 'drafts/*/*/spec.md'` 搜尋內文。

**版本檢查**（必做）：同一個 feature 可能有別人還在改、還沒合併的版本。

```bash
# 主線上有、你讀的版本還沒有的修改（讀 PR 或 commit 時把 HEAD 換成那個 commit）
git log --oneline HEAD..origin/main -- drafts/{sprint}/{feature}/
# 其他遠端分支上還沒合併、有碰到這個 feature 的修改；--source 會標出是哪個分支
git log --oneline --source --remotes=origin --not origin/main -- drafts/{sprint}/{feature}/
```

找到時不要自行改用別的版本：列在涵蓋範圍報告的「版本檢查」，說明分支名稱與改了什麼（`git log --oneline`），提醒 PM 這些修改還沒納入。

### Phase 1 — 建立讀取清單

列出 feature 資料夾的所有檔案（工作目錄用 `ls -R drafts/{sprint}/{feature}/`，指定版本用 `git ls-tree -r --name-only {commit} drafts/{sprint}/{feature}/`），建立一份**讀取清單**，避免漏掉放在旁邊檔案的內容：

- **規格本文**：`spec.md`
- **周邊檔**：`decisions.md`、`actions.md`、`changelog.md`、`design-review.md`、`reviews/`、`meetings/`（實際有哪些以列出的結果為準）
- **引用的其他規格**：本文連到的其他 feature 規格（例：`../page-editor/spec.md`），同一個版本一起讀，版本另外記
- **潛在問題**：讀不到的檔（路徑錯誤、引用的檔不存在於該版本）

### Phase 2 — 完整讀取

依讀取清單逐檔讀取（工作目錄用 Read，指定版本用 `git show {commit}:{path}`）：

1. 讀到新的引用檔就加進讀取清單一併讀取
2. 維護一份已讀集合，避免循環引用
3. 讀不到的內容：在涵蓋範圍報告中記為 `未取得／受阻`，並附上原因

讀周邊檔時特別留意：

- `actions.md` 裡還開著的項目，代表規格在那一點未定，列進 B 段缺漏並引用原項目
- `decisions.md` 的 D-編號、`design-review.md` 的 DR-編號跟本文對不上時，列進 A 段歧義，兩邊原文都引用
- `changelog.md` 標出的新改段落，優先檢查有沒有改了一處、漏改其他處

### Phase 3 — 涵蓋範圍報告

**在做任何分析之前先輸出這份報告。** 它讓 PM（和你自己）知道手上有哪些素材。

```
## 涵蓋範圍報告

- **規格版本**：`drafts/{sprint}/{feature}/spec.md` {版本記法}
- **版本檢查**：{主線的新改動、其他分支還沒合併的修改；沒有就寫「無」}
- **已讀的檔案**：[逐一列出]
- **未取得／受阻**：[逐一列出路徑與原因]
- **假設**：[任何你自行假設的內容 — 盡量少]
- **需要補充的輸入**：[若有缺口，PM 需要提供什麼才能補齊]
```

### Phase 4 — QA Pre-Review Pack

接著分析蒐集到的所有內容。輸出分成三個段落（A、B、C）。

**一律在 Pre-Review Pack 最上方、A 段之前輸出定義表：**

```
### 段落定義

| 段落 | 名稱 | 用途 |
|---------|------|---------|
| A | 歧義 | 規格中語意模糊、不同工程師可能有不同解讀的地方 |
| B | 缺漏 | 規格中缺少的內容（未定義的行為、缺少的規則） |
| C | 風險情境 | 按「影響 × 可能性」排序的風險情境（含負面案例） |
```

最高原則：**絕不捏造規格內容**。有缺漏或模糊之處就直接指出，並提出 2–3 個可能的定義讓 PM 選擇。你的工作是把問題攤出來，不是去解決它們。

優先處理會造成**返工**的問題 — 也就是規格不清楚或自相矛盾，導致工程團隊可能做錯東西的地方。

每一項標上優先度：P0＝答案不同，資料或 API 要重做；P1＝影響驗收條件怎麼寫；P2＝文案、邊角。

A、B 段每一項都編號（`A-1`、`B-1-1`），PM 回覆時才能指名哪一項。

---

#### A. 歧義（附原文引用）

每個歧義都要：

- **引用或標出**規格中確切的句子／段落，附下方「引用格式」
- **說明**為什麼有歧義（可能的解讀有哪些？）
- **提出** 2–3 個可測試的定義，讓 PM／設計挑選

聚焦在不同工程師會有不同解讀的用語。

#### B. 缺漏（規格缺少的內容）

以檢查清單呈現，分成以下 3 組輸出：

**B-1. UI / 前端相關**

- 頁面狀態未定義（空狀態、載入中、錯誤狀態）
- 元件互動行為不明（disabled 條件、hover/focus 狀態）
- 響應式/多裝置行為
- 國際化／時區處理（如有相關）

**B-2. API / 後端相關**

- 不夠具體、無法拿來測試的驗收條件
- 錯誤處理（錯誤碼、訊息、重試行為）
- 資料驗證規則（必填欄位、格式、範圍、唯一性）
- API 回應結構未定義

**B-3. 流程 / 規則相關**

- 沒有完整列出的狀態轉換
- 角色／權限矩陣（誰能做什麼？）
- 空狀態、上限、並行存取相關的 edge case
- 跨模組影響未說明

#### C. 前 10 大風險情境（含負面案例）

依**影響 × 可能性**排序。每一項都要寫出：

- 觸發條件（由什麼引起）
- 預期的系統行為（應該發生什麼；規格沒寫就明講「規格未定義」，並對應到 A 或 B 段的編號）
- 受影響的模組／endpoint（波及範圍）

可從這些方向思考：race condition、資料損毀、安全邊界、第三方服務失效，以及使用者的操作超出規格預料的情境。

---

### 引用格式

規格原文一律附「檔案 版本記法 章節」，例：

`drafts/2613/page-management/spec.md 4.13（c9f5a4c）功能二規則 7；AC 2-7-1`

以章節、規則與 AC 編號定位；行號會隨修改變動，只當輔助。

### Self-Review（輸出完成前必做）

1. **錯字檢查**：掃描所有中英文內容，修正明顯錯字
2. **表格格式確認**：確認所有 Markdown 表格的欄位數一致、對齊正確
3. **引用準確性**：確認 A 段的引用確實逐字存在於該版本的原文中（工作目錄用 Grep，指定版本用 `git show` 核對）
4. **分類一致性**：確認 B 段的缺漏歸類正確（UI/API/流程）

---

## 輸出順序

一律依此順序輸出，這就是你回給助手的完整內容：

1. 涵蓋範圍報告（附讀取清單摘要）
2. QA Pre-Review Pack（A、B、C 段）
3. （選用）附錄 — 周邊檔摘要（開著的待釐清事項、與本文衝突的決定）
4. 給助手的後續步驟（照抄下面這段）：

```
## 後續步驟（給助手）

把上面的報告完整呈現給 PM，然後問 PM 要先處理哪幾項（用 A-n、B-n-n 編號指名）。
- 要改規格：用 pm-spec write 套用，它會一起更新 changelog.md 與 spec_version。
- 這份規格已經有開著的 PR：可以用 pm-ship suggest 把建議寫法留成 PR 上的建議修改。
- 已經決定、只是這一版不做的項目：在 decisions.md 記下決定與理由，QA 預審會把它當成已定案。
- 還沒決定的項目：寫進 actions.md 的待釐清。QA 預審仍會把它列為缺漏，但會引用原項目，知道 PM 已經在處理。
- 改完想確認：帶同一個參數再跑一次 pm-review preflight。
不要自己改 spec.md；改規格一律經過 PM 確認後交給 pm-spec write。
```
