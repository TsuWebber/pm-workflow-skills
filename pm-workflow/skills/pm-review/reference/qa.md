# Spec Review（輕量 PM 版）

## 定位

用 QA 的角度，在**交給工程或設計之前**，幫 PM 快速挑出 `spec.md` 最容易造成返工的問題，
並直接給「建議補法」與「可貼回 spec 的句子」。順帶檢查 user story 的方向對不對、有沒有過度設計。

**這個 skill 只做輕量挑刺**。不做 EARS、RFC、統一語言表、多階段分析、測試計畫、test matrix ——
那是工程交接工具，不在這裡。PM 要的是「還缺什麼、哪裡會做錯」，不是嚴謹需求萃取。

預設語言：繁體中文（技術名詞如 API path、欄位名、狀態 enum 保留英文）。

---

## When To Use

適用：
- PM 剛寫完 / 改完一版 `spec.md`，想在交付前挑刺
- 想知道「這份規格還缺什麼」、做 gap check
- 想找出 RD、設計、QA 可能理解不同的地方
- 想確認某個 user story 方向對不對、是不是做太多

不適用（改用別的）：
- 還在想問題方向、要不要做 → `pm-plan scope`
- 要把內容寫成 / 改成正式規格 → `pm-spec write`
- 要嚴謹的 EARS / RFC 需求交接給後端 → 目前不提供（未來需要再加）

---

## 步驟一：找到要 review 的 spec

這個 skill 對 **spec repo `drafts/` 裡的 `spec.md`** 工作，不對 Notion。

1. 若使用者已指明某個 feature（或給了路徑）→ 讀那份 `drafts/<sprint>/<feature>/spec.md`。
2. 若沒指明 → 列出 `drafts/<sprint>/` 下有哪些 feature 資料夾，請使用者選。
3. 一併讀同資料夾的 `decisions.md`、`actions.md`（了解哪些是「已知待釐清」，避免重複挑），
   以及 frontmatter 的 `spec_version`，據以決定**挑刺的深度**：
   - **還早**（`draft`、`spec_version` 還很低、大量 TBD）→ 挑**大方向**：方向對不對、範圍會不會太大、有沒有解錯問題。
   - **接近定案**（已送審 / `approved`、內容大致完整）→ 挑**細節**：邊界條件、狀態轉換、AC 是否可測。

   > 沒有 `in_review` 這個狀態——**送審中的 spec 仍是 `draft`**。要知道有沒有在送審，看 Gitea 上有沒有開著的 PR，或直接問 PM。

> 若使用者是直接貼一段文字、還沒進 drafts → 先照常挑刺，最後提醒他「這份還沒落地到
> `drafts/<sprint>/<feature>/`，要不要用 `pm-spec write` 建起來」。

---

## 步驟二：挑刺的六個面向

快速回答這幾件事：

**規格層（gap check）**
- 哪裡寫得不夠清楚（同一句有兩種以上合理解讀）
- 哪些欄位 / 規則 / 預設值 / 空狀態 / 異常情境漏了
- 哪些流程前後衝突、或前後台可能結果不一致
- 哪些地方 PM 以為 obvious、但 RD 不一定這樣理解 → 最容易做錯

**user story 層（方向檢查）**
- 這個 story 解的是不是對的問題（對照 `decisions.md` 的問題定義）
- 有沒有 over-engineering（為了不存在的情境加規則）
- 有沒有覆蓋不到的角色 / 情境

**決策層**
- 哪些決策還沒定、但已經影響設計或 RD 開工

---

## 步驟三：輸出報告（對話顯示）

用以下結構，優先級用 🟥🟨🟩：

```
## 規格檢查摘要
- 一句話：目前規格成熟度
- 一句話：最大風險
- 一句話：下一步建議

## 1. 不清楚的地方
### 🟥 高優先｜[問題標題]
**問題點** …
**為什麼現在要補** …
**建議補法**（最多 3 個方向）
- …
**spec 建議寫法**
> …

## 2. 缺少的內容
### 🟨 中優先｜[問題標題]
…

## 3. 可能衝突或容易做錯的地方
### 🟥 高優先｜[問題標題]
…

## 4. user story 方向 / over-engineering
### 🟨 [問題標題]
**觀察** …（解錯問題 / 做太多 / 覆蓋漏洞）
**建議** …

## 5. 建議優先補齊
- 🟥 高優先：…
- 🟨 中優先：…
- 🟩 低優先：…
```

### 優先級定義

| 優先級 | 符號 | 定義 |
|---|---|---|
| 高 | 🟥 | 不補會直接導致工程做錯、返工，或前後台結果不一致 |
| 中 | 🟨 | 不補仍可做，但容易造成理解不一致、設計與工程分歧 |
| 低 | 🟩 | 完整性補充，不影響主要實作方向，可後補 |

---

## 步驟四：落地到 drafts（spec repo 版關鍵）

報告顯示完後，**不要只停在對話**。要把結果沉澱進該 feature 資料夾：

1. **待補項目寫進 `actions.md`** —— 把「建議優先補齊」那幾點，用 checkbox 追蹤：
   ```markdown
   ## 待釐清（來自 pm-review qa YYYY-MM-DD）
   - [ ] 🟥 樣式是否為必填欄位
   - [ ] 🟥 異常商品隱藏後的顯示邏輯
   - [ ] 🟨 商品加入單位與子商品層級規則
   ```
   日期用使用者提供的當天日期；不要自行捏造。追加時**不覆蓋**既有內容。

2. **在 `changelog.md` 補一筆** review 事實（讓下游知道這份被檢查過）：
   ```markdown
   - YYYY-MM-DD pm-review qa：挑出 N 項待補（詳見 actions.md），最大風險為 …
   ```

3. **不改 `spec.md` 本身** —— review 只指出問題，實際改規格是 `pm-spec write` 的事。

> 這些檔案已存在（走 `drafts/_meta/TEMPLATE-*` 建立）。若某檔不存在，提示使用者該 feature
> 還沒照 `drafts/README.md` 建齊，先補建再落地。

---

## 步驟五：收尾

1. 問使用者要先處理哪幾項。
2. 確認清單後提示：
   - 要**立即改規格** → 用 `pm-spec write`（會同步更新 `spec.md` + `changelog.md` + `spec_version`）。
   - 改完要**送出 / 開 PR** → 用 `pm-ship`（git 的事交給它，你不用碰）。
   - 這份 spec 已經有開著的 PR → 可以用 `pm-ship suggest` 把「spec 建議寫法」留成 PR 上的建議修改，作者一鍵套用。
3. **不要**主動輸出 test matrix、P0 flow、EARS、automation 建議 —— 那些不在本 skill 範圍。

---

## Writing Rules

- 一律繁體中文，用 PM / 設計 / RD 都看得懂的語言。
- 先講問題，再講影響，最後給建議寫法。
- 不重寫整份 spec，只指出要補強的點。
- 每個問題盡量附「spec 建議寫法」；內容模糊時給 2–3 個定義方向。
- 簡潔：同類問題合併成一條，「建議補法」最多 3 個，不展開長篇。
- 聚焦真正影響實作的問題，不做窮舉式完整性掃描。

## Example Output

```
## 規格檢查摘要
- 模組方向清楚、主要功能已成形，可往下拆票。
- 最大風險不在缺功能，而在幾個關鍵規則還沒收斂，容易前後台不一致。
- 建議先補：樣式是否必填、異常商品隱藏後的顯示邏輯。

## 1. 不清楚的地方
### 🟥 高優先｜樣式未設定時是否允許儲存
**問題點** 規格只寫「未設定樣式時前台不顯示標示」，沒定義後台是否允許儲存 / 上線。
**為什麼現在要補** 直接影響表單驗證規則，也影響 RD 對「樣式是不是必填」的理解。
**建議補法**
- 方案 A：允許儲存，前台僅不顯示標示
- 方案 B：允許儲存但不可發布
- 方案 C：視為必填，未設定不得儲存
**spec 建議寫法**
> 商品區塊樣式為必填欄位，未設定樣式時不得儲存。

## 4. user story 方向 / over-engineering
### 🟨 「支援 5 種排序」可能做太多
**觀察** decisions.md 的問題是「找不到常用商品」，5 種排序解的不是這個痛點。
**建議** 先做「最近使用 / 名稱」兩種，其餘列 actions.md 待驗證需求。

## 5. 建議優先補齊
- 🟥 高優先：樣式是否為必填欄位
- 🟥 高優先：異常商品隱藏後的顯示邏輯
- 🟨 中優先：商品加入單位與子商品層級規則
- 🟩 低優先：搜尋結果列表顯示欄位補充
```
