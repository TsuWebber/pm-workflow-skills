# review 第二段：用讀者角色審（原 critique）

模擬實際會讀這份文件的人，找出「誰讀完會卡住、會誤解、會回來問」。
第一段（`rules.md`）檢查格式與規則；這一段檢查**內容是否讓讀者能做事**。

輸入：Notion URL、本機檔案，或對話中貼上的內容。

---

## 讀者角色

依文件類型挑 3–4 個最相關的角色，不必全用。

| 角色 | 讀完要能做到 | 常見卡點 |
|---|---|---|
| 工程 | 估時、開始實作 | 規則沒判準、邊界沒寫、資料從哪來不清楚、與既有系統（OMS / 經銷商平台 / ERP）的關係不明 |
| QA | 寫測試案例 | 預期結果無法觀察、條件分支不完整、錯誤狀態沒定義 |
| 設計 | 畫出所有畫面狀態 | 空狀態、loading、錯誤、權限不同時的畫面沒提 |
| 營運 | 知道要準備什麼資料、改什麼作業 | 主檔 / 設定誰維護、上線前要先做什麼 |
| 財務 | 判斷帳務影響 | 金額、稅、分攤、對帳邏輯有沒有變 |
| 物流 | 判斷倉儲作業影響 | 出貨、退貨、驗收流程是否改變 |
| 客服 / 業務 | 回答客戶 / 經銷商 | 對外規則改了什麼、舊單怎麼處理 |
| 主管 | 拍板 | 為什麼現在做、不做會怎樣、成本多少、建議是什麼 |

---

## Workflow

1. 讀 `.pm/PROJECT.md`（若有），確認使用單位與相關部門，據此挑角色。
2. 每個角色從頭讀一次，記下該角色**讀完仍無法做事**的地方。
3. 合併重複問題，依影響排序：會導致做錯 > 會導致來回確認 > 讀起來吃力。
4. 依下方格式輸出。

---

## Output Format

```
## Critique：[文件名稱]

**一句話總評**：[這份文件目前最大的問題是什麼]

### 最需要先處理的 3 件事
1. **[問題]**（影響：工程、QA）
   - 位置：A-2 商品異常警示
   - 為什麼是問題：[讀者會怎麼誤解或卡住]
   - 建議：[具體怎麼補，或改成 🟡 待確認 由誰回答]
2. …
3. …

### 各角色觀點
**工程**
- …
**QA**
- …

### 寫得好的地方
- （1–2 點，指出值得保留的寫法，避免後續修改時被改掉）
```

規則：
- 「最需要先處理」最多 3 件，強迫排序。
- 不重寫文件；只指出問題與修法。使用者要求才動手改。
- 不提格式問題（第一段已處理），除非格式直接造成誤解。
- 結尾一句話建議下一步：問題多屬邊界 → `pm-review edge`；屬跨部門 → `pm-review impact`；屬格式 → 回看第一段的修法。
