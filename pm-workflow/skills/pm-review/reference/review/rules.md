# readers 第一段：依底線規則逐條檢查

對 PRD、AC、決策文件、release note 做**可重複、可逐條對照**的檢查。
不評價方向好壞（那是第二段 `roles.md`），只檢查文件是否違反底線規則。

輸入：Notion URL（用 `notion-fetch` 讀取）、本機檔案路徑，或對話中貼上的內容。

---

## 檢查規則

> 兩種規格格式都適用：Notion PRD 用 `A-x` 區塊，規格庫用 `STORY-xxx` 與 `STORY-xxx · AC-nnnn`。下表的「A-x」在規格庫格式下對應「STORY」。


每條規則有編號與嚴重度。**P0** = 會讓工程 / QA 做錯或無法驗收；**P1** = 會造成誤解或來回確認；**P2** = 可讀性問題。

### 通用（所有文件）

| 編號 | 嚴重度 | 規則 | 怎麼判斷 |
|---|---|---|---|
| G-01 | P1 | 待確認格式統一 | 出現 `TBD`、`待定`、`??`、`**🟡 TBD**` 標題，或 `🟡 待確認` 被集中到文件最後（規格庫模板本身有「待確認」章節時不算） |
| G-02 | P1 | 無空話 | 命中 `../../../../shared/floor.md` §7 黑名單，且同一句沒有具體對象或數字 |
| G-03 | P0 | 規則有判準 | 出現「適當」「視情況」「必要時」「合理」「彈性」，但後面沒有判斷條件 |
| G-04 | P1 | 開放式列舉 | 列舉以「等」「…」結尾，且無「本版僅」限定 |
| G-05 | P2 | 用語一致 | 同一概念在文件內出現兩種以上說法；系統名不符 pm-config 的專有名詞（例：同一系統一下寫「訂單系統」一下寫「OMS」，沒有說明） |
| G-06 | P2 | emoji 位置 | emoji 出現在模板未定義的位置 |
| G-07 | P2 | 空殼段落 | 段落標題下沒有內容，或只有「無」「略」 |
| G-08 | P1 | 權責邊界 | 寫到 pm-config（沒有才看 CLAUDE.md）標為「待確認邊界」的權責，卻直接認定歸屬 |

### PRD（`spec` 產出）

| 編號 | 嚴重度 | 規則 | 怎麼判斷 |
|---|---|---|---|
| S-01 | P0 | Metrics 四要素 | 每個 Success Metric 缺 baseline / target / 衡量方式 / 時間範圍任一項 |
| S-02 | P0 | Scope 有排除項 | Scope 只列包含、沒有寫明本版不做什麼 |
| S-03 | P1 | 每個 A-x / STORY 有功能概述 | A-x toggle 第一行不是 `**功能概述**：` |
| S-04 | P1 | 每個 A-x / STORY 有 User Story | 缺 As a / I want / So that 任一句 |
| S-05 | P0 | 狀態完整 | 有列表 / 表單 / 查詢的 A-x / STORY，沒提到空狀態或錯誤狀態 |
| S-06 | P1 | 不寫內部流程 | 描述「系統呼叫 API」「寫入 table」等實作細節，而非使用者可見結果 |
| S-07 | P1 | AC 區塊存在 | A-x / STORY 底部缺 `☑️ 驗收條件` 區塊 |
| S-08 | P2 | 重複描述 | 功能概述的內容在子主題中又講一次 |

### AC（`ac` 產出）

| 編號 | 嚴重度 | 規則 | 怎麼判斷 |
|---|---|---|---|
| A-01 | P0 | 黑箱可驗證 | Given / When / Then 出現 DB 欄位、API 名稱、log、cache |
| A-02 | P0 | 分支覆蓋 | spec 中的「若…則…」條件分支，沒有對應 Scenario |
| A-03 | P1 | When 單一動作 | 一個 Scenario 的 When 超過一個觸發動作 |
| A-04 | P1 | Then 可觀察 | Then 寫「系統正確處理」「資料正確」等無法目測驗證的描述 |
| A-05 | P2 | 編號格式 | Notion 格式：Scenario 編號不是 `X.Y` 或 X 未對齊 A-x；規格庫格式：不是 `STORY-xxx · AC-nnnn` |
| A-06 | P1 | 待確認已跳過 | 對 `🟡 待確認` 項目生成了 AC |

### 決策文件（`pm-plan decide` 產出）

| 編號 | 嚴重度 | 規則 | 怎麼判斷 |
|---|---|---|---|
| D-01 | P0 | 至少兩個方案 | 只有一個方案，且沒有「維持現狀」對照 |
| D-02 | P0 | 建議明確 | 「建議」段沒有選定單一方案，或寫「都可以」「視情況」 |
| D-03 | P1 | 有寫不處理什麼 | 問題拆解沒有「這次不處理」 |
| D-04 | P1 | 成本 / 影響有寫 | 方案比較表缺成本或影響列 |

### Release Note（`pm-launch release` 產出）

| 編號 | 嚴重度 | 規則 | 怎麼判斷 |
|---|---|---|---|
| R-01 | P0 | 不含待確認 | 出現 `🟡 待確認` 的內容被寫進 release note |
| R-02 | P1 | 使用者語氣 | 出現「系統將會」「後端」「API」「資料庫」 |
| R-03 | P1 | 功能位置是路徑 | 功能位置沒有用「A → B → C」路徑寫法 |
| R-04 | P2 | 目標點數 | 功能目標 callout 超過 3 點 |

## Workflow

1. 判斷文件類型（PRD / AC / 決策文件 / release note），套用「通用」＋對應類型的規則。
2. 逐條檢查，記錄每個違規的位置與原文片段（片段 ≤ 20 字）。
3. 依下方格式輸出。
4. 問使用者要不要直接修正。使用者同意後，在對話中給修正版；寫回 Notion 仍需另外明確指示。

---

## Output Format

```
## Audit 結果：[文件名稱]

文件類型：PRD ｜ 檢查規則：通用 8 條 + PRD 8 條
結果：P0 × N ｜ P1 × N ｜ P2 × N

### P0
| 編號 | 位置 | 問題 | 建議修法 |
|---|---|---|---|
| S-01 | Success Metrics 第 2 點 | 缺 baseline 與時間範圍 | 補「目前 X%，上線後 2 個月內達 Y%」 |

### P1
…

### P2
…

### 通過
G-04、G-06、S-03 …（只列編號）
```

規則：
- 沒有違規的嚴重度區塊整段省略。
- 「建議修法」要具體到可以直接改，不寫「請補充」。
- 不新增規則表以外的問題；方向性問題留給第二段處理。
