# pm-spec reverse

你要從**實作反推現況**,為指定功能產出 Userflow——使用者實際走得完的路徑,不是規劃中的路徑。

**規範一律依 [specs/docs/USERFLOW-WRITING-GUIDELINES.md](../../specs/docs/USERFLOW-WRITING-GUIDELINES.md)**,本指令不重複規則內文。

## 輸入

- **前端 repo 路徑**:`$1`(必填。使用者實際看到什麼畫面、按鈕在哪一頁、按下去跳到哪,只存在於前端實作裡)
- **要生成 flow 的功能**:`$2`(可能是多個詞)
- **後端 repo 路徑**:`$3`(選填。僅用來確認結束狀態的欄位名與狀態 enum;它無法告訴你使用者走了幾頁)

完整參數:`$ARGUMENTS`

前端路徑或功能缺漏時先詢問,不要自行臆測路徑。

## 工作流程

### 1. 必要性檢查（先判斷要不要寫）

依規範 §4 的必要性矩陣比對該功能。全部落在「不寫」欄 → 停手並回報理由,建議改跑 `pm-spec reverse`。
只命中「選寫」→ 詢問使用者。答不出「產出後誰會讀」就停手。

### 2. 定位 app

- 從前端 repo 的 monorepo 結構找出功能所屬的目錄,那個目錄名就是 `app` 與輸出資料夾名(規範 §7.2)。
- **先判斷這是單站程式還是共用模組**:功能由多個部署站共用(例:多品牌官網共用的認證模組)時,`app` 取該共用模組的目錄名,不要在每個站的目錄各產一份。
- 品牌代碼(`projectCode`)、選單配置、角色權限的差異**不另開 app**,寫進 flow 的前置條件。

### 3. 讀前端還原路徑

優先看:route 定義、page/view、跳轉與導覽邏輯、表單送出後的處理、i18n 文案(取使用者看得到的字)。
目標是還原**使用者動作與看得見的系統回應**,不是抄元件結構或 API 呼叫。

**每個使用者動作都要對得上一個實際的畫面元件**——按鈕、連結、輸入欄位、拖放區、對話框其中之一。
記下該元件所在的檔案,產出後要能逐條回查。對不上元件的動作不是路徑,不要寫進主線或分支。

**證據要抓「使用者看得到的文字」,不是函式名或元件名**(規範 §7.1):

| 證據 | 可用? |
|---|---|
| 畫面文案字串(按鈕文字、提示訊息、欄位標籤) | ✅ 足夠 |
| 元件檔名(`DialogXxx`) | ⚠️ 只證明元件存在,不證明使用者進得去 |
| 事件處理函式(`handleXxx`) | ❌ 函式存在不代表按鈕會渲染,可能被條件隱藏 |

做法:對每個候選動作,**grep 該動作的畫面文字**(中文字串或 i18n key),找不到就不要寫。
找到文字後再確認它的渲染條件——包在 `{false && ...}`、環境判斷或權限判斷裡的,要一併寫進判斷依據或前置條件。

⚠️ **`_index.md` 或 spec 的流程敘述不是路徑來源。** 文件常把跨畫面、跨系統的環節寫成一條順序鏈
(例:「上傳檔案 → 打包下載 → 匯入」),但那是業務流程的敘述,不代表這些動作出現在同一個畫面、
更不代表順序相同。**只能拿它當「該去找哪些畫面」的線索,不能直接當步驟或分支。**

### 3.5 比對 story，標出無出處的規則

- 讀前端讀到的每一條**行為規則**（顯示條件、倒數秒數、警示門檻、自動觸發時機），先到該模組 `stories/` 與 `_index.md` 查有沒有出處。
- **查無出處的不要寫進 flow**：依規範 §3.4 列進「待回填 story」清單，在回報結果中單獨呈現。
- 純畫面呈現（版面、文案、格式）依規範 §9 直接排除。

這一關是為了避免 flow 變成某條規則的唯一出處。

### 4. 切出使用者目標

依規範 §2 把功能切成數個 sea level 目標,每個目標一條 flow;標題「角色 + 動詞 + 受詞」。
`actor` 用業務角色(客服人員、倉管、消費者),禁用 RD / QA / 前端 / 後端。

### 5. 依規範 §3 檢查複雜度並拆條

- 主線超過 9 步 → 按穩定狀態切兩條。
- 出現異步接力(換 app、換操作者身分) → 依 §3.1 拆條,`continues-to` / `continues-from` 互指。
- 分支只留改變結束狀態的,最多 4 條、不嵌套。

### 6. 用後端確認結束狀態（有給 `$3` 時）

查對應的 controller、service、model 狀態欄位,把結束狀態寫成實際的狀態值(例 `pending_payment`),不要寫「訂單成功」這種模糊說法。

### 7. 決定歸屬並對應 story

- 依規範 §7.3,以 flow **結束狀態所在的 feature** 決定歸屬;途經的其他模組填進 `spans`。
- 掃該 feature 的 `stories/` 目錄,把對得上的 story 檔名填進 `story-refs`;對不上標 `TBD（無對應現有 story）`。

### 8. 輸出

- 位置:`specs/docs/<模組>/<feature>/userflows/<app>/<flow-slug>.md`,**一檔一條 flow**。
- `userflows/` 與該 feature 的 `stories/` 同層並列;資料夾不存在則建立。
- 檔名 kebab-case、動詞開頭,對齊使用者目標(`create-order-for-member.md`)。
- 內容依規範附錄的模板;`fe-route` 必填(程式碼裡查得到)。
- 使用者另有指定輸出位置則以使用者為準。
- 產出後回報檔案路徑清單與每條 flow 的目標、結束狀態。

### 9. 自我檢驗（產出前逐條確認）

- **每個使用者動作都指得出對應的畫面元件嗎?**(逐條回查步驟 3 記下的檔案;指不出來的就是推論,刪掉)
- **每個動作的證據是畫面文案,而不是函式名或元件名嗎?**(只有函式名的要回去 grep 文案)
- **有沒有動作的元件其實被條件隱藏?**(`{false && ...}`、環境或權限判斷)
- 這條路徑**現在真的走得通**嗎?(反推現況,不是寫規劃)
- 版面全部重畫後這條 flow 還成立嗎?(規範 §8 穩定性)
- 有沒有把 story 的業務規則抄進來?
- 有沒有把 `_index.md` 的流程敘述當成畫面動作順序?
- 送審前檢查清單(規範附錄)每一項都過了嗎?

逐條答完再產出。

## 定位與分工

- **與 `pm-spec reverse` 的分工**:story 管**憑什麼**(業務規則與判斷依據),flow 管**怎麼走**(路徑與導覽)。`pm-spec reverse` 輸出到後端 repo 的 `specs/`;本指令輸出到 spec repo 的 `specs/docs/<模組>/<feature>/userflows/`。
- **與 `pm-spec flow` 的分工**:本指令描述**現在跑著的**(as-is),`pm-spec flow` 描述**將來要做的**(to-be)。兩者依同一份規範,差別只在取材對象、輸出位置與檔案粒度(規範 §7.1)。
- **`specs/` 的編輯界線**:本指令只新增 `userflows/` 子目錄的檔案,不改動 `_index.md` 與 `stories/`(後端規則由 oms 同步,改了會被覆蓋)。
