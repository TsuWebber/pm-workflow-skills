# impact：跨部門影響盤點

一個需求在 PRD 裡只寫系統行為，但實際上線會牽動營運、財務、物流、客服等部門的作業。
這個指令盤點每個部門**受到什麼影響、需要他們做什麼、需要他們拍板什麼**，避免上線前才發現沒人準備。

輸入：PRD、決策文件、或需求描述。

---

## 部門清單

以全域 `CLAUDE.md`「部門職責」為準：

| 部門 | 通常會被影響的地方 |
|---|---|
| 產品 | 商品規格、SKU 規劃（預組 / 非預組） |
| 營運 | 商品主檔、SKU 分類欄位、BOM 建置與維護、商場設定 |
| 財務 | 會計科目、成本 / 收入認列、BOM 分攤、發票、對帳報表 |
| 物流（倉儲） | 進貨驗收、揀貨包裝、退貨驗收、次品 / 報廢 / 福利品判斷 |
| 生管（PMC） | 供應商生產排程、封裝流程、配合 ERP 轉換的庫存作業 |
| 客服 | 2C 客戶退換貨受理、客訴、新規則上路的溝通 |
| 業務 | 2B 經銷商 / 月結客戶端事務 |
| 增長傳播 | 對客戶的政策說明、通知文案 |

CLAUDE.md 未涵蓋的部門（技術、法務、人資等），若需求明顯涉及，列入並標 `🟡 待確認：權責歸屬`。

---

## Workflow

1. 讀 `.pm/PROJECT.md` 的「相關部門與決策者」（若有），取得窗口名單。
2. 逐一判斷每個部門是否受影響；不受影響的直接略過，不列。
3. 對受影響的部門，回答四件事：
   - **影響**：哪個作業、報表、規則會改變
   - **要他們做**：上線前 / 上線當下 / 上線後要配合的事
   - **要他們拍板**：需要該部門決定的規則（對應 PRD 的 `🟡 待確認`）
   - **時機**：最晚什麼時候要溝通（規格確認前 / 開發前 / 上線前 / 上線後）
4. 涉及 CLAUDE.md 標為「待確認邊界」的權責（例：BOM 原始資訊來自生管、維護在營運），明確標出交接點未定。

---

## Output Format

```
## 影響盤點：[需求名稱]

受影響部門：營運、財務、客服 ｜ 需拍板事項 N 個

| 部門 | 影響 | 要他們做 | 要他們拍板 | 時機 |
|---|---|---|---|---|
| 營運 | 組合商品需維護 BOM | 上線前補齊 120 個預組 SKU 的 BOM | — | 開發前 |
| 財務 | 退貨金額依 BOM 分攤回沖 | 確認對帳報表欄位 | 🟡 分攤採成本法或售價法 | 規格確認前 |
| 客服 | 組合商品不可部分退 | 更新客服話術 | — | 上線前 |

### 權責未定
- 🟡 待確認：BOM 組成比例由生管提供、營運建檔，交接格式與時程未定

### 建議溝通順序
1. 財務（有拍板事項，卡規格）
2. 營運（有前置作業，卡開發）
3. 客服（上線前知會即可）
```

規則：
- 表格只列受影響部門。
- 「要他們拍板」與 PRD 的 `🟡 待確認` 對齊；若 PRD 沒有對應的待確認，建議補上。
- 溝通順序依「有拍板事項 > 有前置作業 > 只需知會」排序。
- 不代替部門做決定；只列出需要決定的事。
