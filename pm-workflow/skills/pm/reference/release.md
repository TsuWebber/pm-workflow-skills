
# release：Release Note（原 Release Note Mode）

## Overview

把 PRD 或功能說明轉成給「使用單位」看的 release note。
不是寫給工程師或技術審查的，而是讓業務、營運、客服等使用方快速理解「這次上了什麼、怎麼用、對我有什麼影響」。

預設輸出語言：繁體中文。
預設輸出位置：**對話框中**。不自動寫入 Notion，需使用者確認草稿後再執行寫入。

---

## When To Use

適用情境：
- 功能上線前要準備使用者溝通文件
- 使用者說「幫我寫 release note」、「整理一份給業務看的說明」
- 使用者提供 PRD URL 或功能描述，要轉成可對外發布的說明

不適用情境：
- 使用者要技術 changelog 或版本更新日誌
- 使用者要撰寫規格 → `spec-write`
- 功能尚未確認，還在討論階段 → `spec-plan`

---

## Release Note Types

### Type A：新功能上線

首次推出的功能，使用者之前沒有類似的操作方式。
著重說明：這個功能的目標、使用對象、操作流程。

### Type B：改版 / 體驗優化

既有功能的 UI / 流程改動，使用者原本就有類似功能。
著重說明：改了什麼、為什麼改、新舊差異在哪（before / after）、新操作怎麼走。

若同時包含新功能 + 改版元素，以改版格式為主，並在操作流程中補充新功能部分。

---

## Workflow

### Step 1：判斷類型與收集資料

若使用者提供 Notion PRD URL：
- 使用 `notion-fetch` 讀取頁面內容
- 提取：功能目標、使用對象、功能位置、操作說明、改版前後差異

若使用者提供純文字描述：
- 直接根據描述整理，缺少欄位做最小合理假設並標示

判斷 Type A 或 Type B，決定輸出結構。

### Step 2：撰寫草稿

依 Type A / B 結構輸出草稿。
語氣與用字對象是「使用單位」，不寫系統內部邏輯，不寫 API 或技術術語。

### Step 3：在對話呈現草稿

輸出後說明：
- 哪些欄位是根據 PRD 內容填入
- 哪些欄位是合理假設（需使用者確認）
- 是否需要補充截圖或連結

### Step 4：等待使用者確認

不自動寫入 Notion。等使用者說「ok 寫進去」或類似確認後，執行 Step 5。

### Step 5：寫入 Notion

將確認後的 release note 以 Notion enhanced markdown 格式寫入指定頁面。

## Writing Rules

- 一律使用繁體中文
- TA 是使用單位（業務、營運、客服），不是工程師
- 不寫系統內部邏輯、API 說明、資料庫欄位
- 不寫「系統將會⋯」「後端邏輯⋯」等技術語氣
- 優先寫「你現在可以⋯」「改版後⋯」等使用者視角語氣
- 操作流程步驟要簡單、口語、可執行
- 功能目標的 callout 控制在 1–3 點，不要太長
- 截圖部分：先產文字草稿，確認後再補截圖
- 若從 PRD 讀取，忽略 🟡 待確認 的項目，不寫進 release note
- 不自動寫入 Notion，需使用者明確確認才執行

---

## Section Rules

### ✅ 功能目標 / 功能改善

- 這是整份 release note 的開場
- 用 🎯 callout（gray_bg）呈現
- 說明這次上線的核心意圖，不要羅列功能清單
- 用使用者感受到的結果來描述，例如「業務人員可以更快⋯」而非「系統新增了⋯」

### 📍 功能位置

- 讓使用者知道去哪找這個功能
- 用路徑寫法，例如：後台 → 首頁編輯器 → 商品模組
- 若功能在多個頁面，逐條列出

### 👤 使用對象

- 說明這個功能或改版影響哪些角色
- 可寫使用情境，例如：「主要影響需要每日操作首頁排班的營運人員」

### ⏪ 操作流程

- 步驟用數字條列
- 每步一個動作，不要塞太多事情進同一步
- 若步驟有截圖，寫在步驟後面（text first，圖補充）
- 若流程有分支（角色不同 / 條件不同），可用小標分段

### 🎨 介面優化重點（改版專用）

- 使用 columns 格式呈現新版 / 舊版截圖
- 截圖下方加文字說明變化重點
- 若沒有截圖，改為文字描述新舊差異

### 👣 新流程步驟（改版專用）

- 若操作步驟有明顯改變，在介面優化重點後列出新流程
- 一樣用數字條列、清楚口語

### ➡️ 下階段優化（選填）

- 若有後續計畫要告知使用單位，在此說明
- 若無，直接省略這個區段，不留空殼

### 💼 開發紀錄

- 固定用 table 格式
- 欄位：上線時間、相關 Jira、PM、設計、工程
- 若資訊不足，留空，不要亂填

---

## Behavior When Information Is Missing

- 若 PRD 有功能目標但無詳細步驟，根據功能邏輯做合理推測，並在草稿末標示「⚠️ 以下步驟為草稿推測，請確認後調整」
- 若使用對象 PRD 未明確說明，根據功能性質判斷，並標示假設
- 若改版但無舊版截圖，columns 欄位改為文字描述舊版樣子
- 若 PRD 有 🟡 待確認 項目，不寫進 release note，等確認後再補

## End Condition

草稿輸出完成後，等待使用者確認。
確認後執行 Notion 寫入，將 release note 填入指定頁面。
若使用者要求調整特定段落，在對話中修改後，再重新寫入。
