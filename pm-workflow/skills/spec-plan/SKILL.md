# Spec Plan（動筆前想清楚）

## 定位

在 PM 開始寫規格**之前**，把三件事做完：
1. **載入 context** —— 這個功能會碰 spec repo 裡哪些模組、有哪些已知限制 / 落差。
2. **框架問題** —— 用 Socratic 對話確認「解的是對的問題、有根據」。
3. **收斂方向** —— 背景、目標順序、（必要時競品）、功能拆分，收斂到「方向」層級。

完成後**建立 feature 資料夾骨架**、把方向沉澱進 `decisions.md`、把待釐清放進 `actions.md`，
交棒給 `spec-write` 寫完整規格。

**這個 skill 不寫完整 spec**。它產出的是「想清楚的結論 + 資料夾骨架」，不是 `spec.md` 內文。

預設語言：繁體中文（技術名詞保留英文）。

---

## When To Use

適用：
- PM 有個想法 / 問題，還沒確定要不要做、怎麼做
- 「我想做 X」「我們要解決 Y」「用戶一直抱怨 Z」「這個要不要做」
- 要開一個新 feature、需要先建資料夾骨架

不適用（改用別的）：
- 方向已清楚、要直接寫規格 → `spec-write`
- 已有 spec、只想挑問題 → `spec-review`
- 開完會要整理成決策 / 待辦 / spec 增補 → `/meeting-to-actions`

---

## Step 0：判斷功能類型

第一個問題固定問：**「這是新功能，還是優化 / 改既有功能？」**
兩條路徑的重點不同：

| | 新功能 | 優化功能 |
|---|---|---|
| context 重點 | 會新增 / 連動哪些模組 | 現有模組邏輯是什麼、改了影響哪裡 |
| ⚠️ 限制風險 | 低 | 高（改既有邏輯容易命中限制） |
| 額外確認 | 無 | PM 對現有行為是否清楚，不清楚先讀現況規格 |

---

## Step 1：載入 spec repo context（取代 architecture.md）

spec repo 本身就是模組地圖。依功能領域讀對應區塊，找出會碰到什麼：

1. **看現況全貌** → 對應模組 `specs/docs/<模組>/_index.md`；不確定是哪個模組看 `index.md` 的導覽表。
2. **看後端邏輯** → `specs/docs/` 的 8 大模組（訂單生命週期 / 金流與發票 / 出貨與物流 / ERP 整合 / 商品與行銷 / 會員與權限 / 外部平台整合 / 系統基礎設施）。
3. **看畫面行為與 URL 對照** → 對應模組 `specs/docs/<模組>/_index.md`（含原 frontend 的頁面/Dialog 商業規則與 Route Mapping 表）。

輸出「模組連動確認」：

```
📦 模組連動確認
功能類型：[新功能 / 優化功能]
主要模組：[會發生在哪，附連結，例 [coupon](specs/docs/05-product-and-marketing/coupon/_index.md)]
連動模組：
- [模組名](specs/docs/<模組>/<capability>/_index.md) — [為何連動]
⚠️ 已知限制 / 落差：
- [限制或現況落差] → 你打算怎麼處理？
📊 數據支持：
- 有哪些數據支撐這個需求？沒有 → 標記為假設，寫進 decisions.md。
```

> 找不到相關模組資料 → 請 PM 直接說這次會碰哪些功能，或先請工程窗口補現況規格。
> **優化功能**：若 PM 對現有行為不清楚 → 先讀對應 `specs/` 模組規格或請工程說明，再往下，否則容易改錯方向。

已知限制不是擋路，是提醒 PM 在方向裡要有對應說明（繞開 / 需工程評估 / 本次不影響三選一，**不能沉默跳過**）。

---

## Step 2：問題框架確認（Socratic 提問）

不是質疑 PM，是幫 PM 動手前把問題說清楚。

**路徑 A（新功能）**
- A1 問題來源：「為什麼需要？來源是什麼？」模糊（「感覺缺」「競品有」）→ 追問有沒有用戶明確需求。
- A2 用戶與範圍：「給誰用？影響多少人 / 情境？」「所有人都要」→ 追問哪類最迫切。
- A3 MVP 邊界：「做到什麼程度算完成？哪些之後再說？」說不清 → 幫列 2–3 個候選邊界讓他選。

**路徑 B（優化）**
- B1 現狀問題：「現在哪裡不夠好？具體是什麼？」模糊 → 追問誰覺得、什麼操作下發生。
- B2 現狀數據：「有描述現狀的數據嗎（客訴數、完成率、錯誤率）？」沒有 → 「先確認再規劃，或標記假設繼續，你選哪個？」
- B3 成功定義：「優化後怎樣算成功？可量化嗎？」沒有 → 幫提 2–3 個候選指標讓他選。

**放行判斷**：A 路徑 A1–A3、B 路徑 B1–B3（B2 可標假設）都有清楚回答才放行。

**反理性化（這一段不得跳過）**
- 「先寫再說」→ 問題不清楚，方向會錯。
- 「很急」→ 急更要說清楚，否則要重做。
- 「很小的改動」→ 小改也要知道為什麼改、改到哪。
- 「上面說要做」→ 仍要確認用戶問題，否則無法評估範圍。

---

## Step 3：收斂方向

先判斷 PM 帶來的是**冷啟動**（只有一句話 / 關鍵字）還是**有材料**（流程、訪談、畫面、研究）。

- **冷啟動**：每輪最多問 2 題，依序挖「問題核心 → 影響對象 → 成功樣貌」，最多 3 輪，三者有初步答案就進入收斂。
- **有材料**：先收斂「這批在講什麼、可切成哪幾個重點」，再視需要展開。

收斂到**方向層級**即可（不要展開成 spec 明細）：
- 背景與現況
- 目標與優先順序
- 競品（只在 PM 要求時，聚焦 2–4 個，指出「適合參考什麼」）
- 功能拆分（先拆大功能區塊 + 定位，不要太早拆細；單一路徑流程不強拆 tab）

> 每輪先短、先收斂，不一次補齊所有章節；保留討論感，不要過早寫成定稿。

---

## Step 4：落地到 drafts（spec repo 版關鍵）

放行且方向收斂後，建立 feature 資料夾骨架 —— **這是本 skill 的實際產出**：

1. **確認 sprint 與 slug**：問「這個放哪個 sprint？」（如 `2607`）、給 feature 一個英文 slug（如 `product-master`）。
2. **建 `drafts/<sprint>/<feature-slug>/`**，從 `drafts/_meta/TEMPLATE-*.md` 複製四檔 + `meetings/`：
   `spec.md`、`decisions.md`、`actions.md`、`changelog.md`。
3. **`decisions.md` 寫第一則 `D-1`（問題定義與方向）**：背景 / 問題、考慮過的選項、方向決定、來源；把 Step 2–3 的結論寫進去。數據不足處標「假設」。
4. **`actions.md` 填 open questions**：Step 1 的限制處理、待確認數據、未定範圍，用 🔴 BLOCK / 🟠 次高 / ⚪ 低風險 分級。
5. **`spec.md` 只填骨架**：frontmatter（`title` / `feature` / `sprint` / `discipline` / `owners` / `refs`）+ 「1. Goal & Success Criteria」「2. Scope (In / Out)」先寫方向共識；**其餘章節留白給 `spec-write`**。
6. **`changelog.md` 記一筆**：`<日期> · sprint <x> · spec_version 0.1` — `[新增] 初版骨架建立（spec-plan）`。日期用使用者提供的當天日期，不自行捏造。

> 資料夾 / 檔案的建立**不需要 PM 碰 git**；之後要送出用 `/ship`。

---

## Step 5：收尾與銜接

放行落地後：
1. 一句話摘要問題定義與方向結論。
2. 提示下一步：**用 `spec-write` 把方向寫成完整 `spec.md`**。
3. 若功能涉及**算法 / 數字 / 門檻** → 提醒：「`spec-write` 會先走指標確認（定義、資料來源、合理性）再寫。」
4. 若還要**開會討論** → 原始記錄丟 `meetings/<日期>-<主題>.md`，會後跑 `/meeting-to-actions` 整理成決策 + 待辦 + spec 增補提案。

---

## Writing Rules

- 一律繁體中文，語言 PM / 設計 / RD 都看得懂。
- 每輪先短、先收斂，不一次展開太多；只問真正能推進決策的 1–2 題。
- 不寫完整 spec 內文（那是 `spec-write`）；本 skill 只到「方向 + 資料夾骨架」。
- 跨檔引用一律用相對 markdown 連結，指到具體檔案（含 `.md`）。從 `drafts/<sprint>/<feature>/` 引用現況規格要退三層，例 `[order-management](../../../specs/docs/01-order-lifecycle/order-management/_index.md)`；對話中回報時用 workspace 根相對路徑即可（例 `[order-management](specs/docs/01-order-lifecycle/order-management/_index.md)`）。不要用 `[[...]]` wiki 連結。
- 未定案的不臆測 → 進 `actions.md`；「為什麼」進 `decisions.md`。
